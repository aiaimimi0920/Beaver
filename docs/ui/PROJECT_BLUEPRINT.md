# 项目规划交互契约

版本：0.1.7。状态：可操作的 UI 原型，等待用户体验后确认。不是自动制作能力已经完成的声明。

0.1.8 补充：[引擎能力功能包目录](ENGINE_PACKAGES.md)新增 68 项能力规划，与原有 10 个源码包合计 78 项可选择。功能块工作区改为“功能包规划 / 源码包”两个页签，前者仅保存选择，后者保持真实接入；其余规划和执行分离约定不变。

0.1.9 补充：[游戏总览契约](PROJECT_OVERVIEW.md)统一基础设定的展示和编辑。创建后默认进入总览且锁定；“项目设置 / 基本设定”不再直接编辑类别等字段，改为跳转总览，原功能规划保留。以下字段含义继续有效，既有编辑入口描述以 0.1.9 契约为准。

## 1. 本轮边界

先一起确定界面、每个选择的含义和未来交付目标，再接入具体业务。用户安排目标，Codex 将来自行拆分；三个制作阶段是人类表达重点的入口，不是要求用户编排 AI 工作流，也不强制按顺序通关。

- 创建仍会复制所选初始模板，形成真实本地 Godot 工程。
- 新增规划只写 Beaver SQLite 中的项目记录，不写游戏目录、不生成素材、不创建任务、不部署服务器、不发送邮件、不发布或付费。
- “预览阶段任务”展示计划中的交付格子，不伪造执行进度或完成结果。
- “保留草案”保留当前编辑内容，顶部“保存规划”才持久化。
- 旧有任务、素材、功能块接入、试玩、导出仍然真实可用；它们不是本轮新增规划按钮的替身。新规划暂不注入实际 Codex 提示词。

## 2. 页面结构

创建弹窗：**基本信息 -> 创作方向 -> 功能规划**。可以往返调整，创建操作只提交一次；正文滚动，底部操作保留可见。

左侧“项目设置”：**基本设定 / 设计 / 开发 / 后期 / 发行准备**。项目设置与左下角全局“设置”区分：前者面向这个游戏，后者面向本机工具与 AI 服务。没有移动旧侧栏图标锚点。

遵守 Loom 紧凑壳层：默认 1120 x 760、最低 960 x 680，侧栏 186 / 52、顶部 50，保留统一通知。阶段只展开当前选中项的含义，不为每个控件堆叠解释性副标题。

## 3. 创建和基本设定

| 控件 | 确定的含义 | 当前行为与未来边界 |
| --- | --- | --- |
| 项目名称、存放目录 | 真实工程的名称与父目录 | 创建子目录；不覆盖已有同名目录 |
| 游戏模板 | 首次创建的工程骨架 | 只在创建时应用；不允许在已修改工程上重新套模板 |
| 主类别 | 核心玩法组织方式 | 必选 1 个，不代表玩法已经完成 |
| 副类别 | 辅助玩法方向 | 可不选；不得与主类别重复，最多 1 个 |
| 游戏主题 | 世界、题材和情境 | 49 个预设之一，或单一自定义主题，不是多选标签 |
| 自定义主题 | 用户自己的原创描述 | 去除首尾空白后 1–120 字符，不自动改写 |
| 表现风格 | 素材和运行画面的表现目标 | 保留像素、手绘、简约 2D、低多边形、风格化 3D、文字六项；不自动转换模板 |
| 目标评级 | 创作内容尺度和受众目标 | 全年龄 / 青少年 / 成年人；不是取得平台或地区分级认证 |
| 游戏规模 | 系统、内容与资产的制作复杂度目标 | 独立 / 标准 / 大型 / AAA；不是游戏时长、地图面积或交付质量保证 |
| 功能规划 | 希望将来加入的可组合功能 | 可加入推荐、勾选或清空；0.1.7 创建时不再调用功能块接入任务 |

评级的 Beaver 解释：全年龄以温和表达为目标；青少年可有成长、适度紧张和冲突；成年人可讨论更复杂沉重的主题，但仍需明确具体边界。选择成年人不解除模型服务限制，也不代表素材自动合规。明显成人向类别/主题与非成年人目标冲突时显示错误，由用户更换选项，不暗中提高评级。

规模的 Beaver 解释：独立优先一个完整核心循环；标准包含多个协作系统和章节/关卡；大型需要分批内容生产与持续验收；AAA 是长期高复杂度目标，不表示预算、团队、工期或品质已具备。四项不是 City Game Studio 的经营数值模拟。

已有 0.1.6 的卡牌类别以“卡牌（已有项目）”保留；旧校园、治愈、自然、悬疑主题映射为自定义文字，不因扩展目录丢失原意。旧时长范围不强行等同新规模，旧 `design` 本身保持不变。

## 4. 在线多人和服务器规划

必须在创建时可表达，以便未来制作从一开始选对网络架构。已有项目也能编辑草案，但本轮切换开关不会重构游戏。未来将单机改为在线需单独任务和验收。未勾选表示不规划在线多人，不等于已经实现本地合作模式。

| 控件 | 含义 | 校验 |
| --- | --- | --- |
| 在线多人游戏 | 是否把在线联机作为项目要求 | 大型多人在线角色扮演类别要求开启，否则提示更换类别 |
| 联机架构 | 专用权威服务器，或玩家主机 + 中继 | 都是设计选择，不是提供商或已部署服务 |
| 目标服务区域 | 面向玩家的服务地理区域 | 去除首尾空白后 1–120 字符 |
| 每局 / 房间人数 | 一个同时交互会话的目标容量 | 2–10000 整数 |
| 峰值同时在线人数 | 整个服务同时在线玩家的目标峰值，即 CCU | 2–10000000 整数；在线时不得小于每局人数 |
| 初期服务器 / 中继实例数 | 计划部署的初期进程实例数量 | 1–100000 整数；不自动推算吞吐、费用或机器配置 |

人数上限只是输入保护，不代表技术可行性承诺。选择玩家主机 + 中继不自动生成公网地址、NAT 穿透或鉴权服务。未来需要结合实际同步模型、服务商规格和真实负载测试确定资源。

关闭联机保留容量草案，重新开启可继续编辑；离线时网络优先级禁用，旧值保留。无效或空白容量字段仍可见、可修正，不允许把错误藏在关闭的区域后面。当前没有“服务器运行中”之类虚假状态。

## 5. 三阶段的十五项含义

当前采用 **独立 0–5 投入优先级**：0 不额外投入，3 标准关注，5 核心重点。不是完成百分比，不要求每阶段总和固定，不保证数值提高就有更多内容。存档安全、基础可用性等必要工作不会因某项为 0 被省略。该模型是本轮可调整的交互选择，尚未宣称用户已确认固定预算分配方式。

| 阶段 / 控件 | 表达的目标 | 未来应交付 | 人类验收着眼点 |
| --- | --- | --- | --- |
| 设计 / 故事性 | 世界观、叙事结构、分支和结局 | 大纲、章节节拍、分支条件与文本约束 | 剧情支持玩法，分支有明确结果 |
| 设计 / 角色 | 动机、关系、造型和语言一致性 | 角色设定、关系图、立绘和对白规范 | 角色可辨认且不自相矛盾 |
| 设计 / 游戏性 | 核心循环、规则、反馈和难度 | 玩法规则、操作流程、原型目标 | 玩家知道行动目的和反馈 |
| 设计 / 图像 | 游戏内视觉、材质、光照与素材一致性 | 风格板、素材规格、场景视觉基准 | 运行画面清楚统一，区别于宣传插画 |
| 设计 / 用户界面 | 游戏内菜单、HUD、信息层级与输入反馈 | 界面流程、布局与键鼠/手柄交互稿 | 操作容易发现，不遮挡玩法，错误有反馈 |
| 开发 / 物理 | 碰撞、运动、接触和模拟稳定性 | 运动规则、边界案例测试目标 | 不穿透、不抖动，行为符合玩法 |
| 开发 / 人工智能 | 游戏中的 NPC、敌人和策略行为 | 状态、决策规则、难度方案 | 行为可解释、可测试、不持续卡死；不是配置 Beaver 模型 |
| 开发 / 声音 | 音乐、音效、语音、混音与触发 | 音频清单、声音风格、播放约定 | 反馈匹配、音量稳定、素材有使用权 |
| 开发 / 模组 | 玩家扩展游戏的接口和数据格式 | 扩展边界、装载与版本约定 | 扩展错误可诊断，不破坏游戏和存档；不是功能块集市 |
| 开发 / 网络 | 同步、房间、鉴权、断线恢复和协议 | 拓扑、同步模型、房间流程、压测目标 | 在真实目标容量下验证延迟和恢复 |
| 后期 / 动画 | 角色、环境和交互动画衔接 | 动画清单、状态切换、事件规范 | 动作与玩法状态同步 |
| 后期 / 优化 | 帧率、内存、加载、包体和设备适配 | 性能预算、基准场景、优化清单 | 真实测量，而非只显示完成标记 |
| 后期 / 插画 | 封面、宣传图、章节插画等独立成图 | 构图、规格、渠道尺寸变体 | 符合风格和评级，各尺寸主体清楚 |
| 后期 / 教程 | 新玩家学习路径和提示节奏 | 分步引导、跳过与重看方案 | 能理解核心操作，不强迫重复教学 |
| 后期 / 过场动画 | 叙事演出、镜头、字幕、进出玩法 | 分镜、时序、字幕、跳过规则 | 可跳过，不丢状态，兼容存档恢复 |

点击项名或聚焦滑块查看右侧含义。“未来交付”“验收目标”是预期，不代表已有对应文件。阶段任务预览也不锁定 Codex 将来的拆分方式。

## 6. 发行准备

| 入口 | 当前可操作内容 | 未来业务目标 |
| --- | --- | --- |
| 联系媒体发布 | 选择游戏媒体 / 评测作者 / 内容创作者，记录约束 | 简介、截图、媒体包、联系人和发送记录；对外发送需明确确认 |
| 发布试玩版 | 选择 itch.io / Steam / 自有页面，记录试玩范围 | 可玩构建、存档隔离、渠道资料、反馈入口；真实发布与现有本地导出分开 |
| 进行广告宣传 | 选择社交媒体 / 视频平台 / 广告网络，记录受众、排期和预算 | 宣传素材、排期、待批准预算；真实投放需另行确认，不默认花费 |

每项“规划”打开编辑弹窗，“取消”丢弃该弹窗修改，“保留草案”回到项目未保存状态。只有“尚未规划 / 已有规划草案 · 未执行”，没有伪造媒体回复、发布成功、下载量、收入或广告转化数据。Epic、微信小游戏适配、自有市场及实际多渠道发行仍是后续目标，不因试玩列表出现 Steam 而宣称已实现。

## 7. 保存、接管与版本

- `Project.blueprint` 是版本 1 的本地规划结构，`blueprintRevision` 随保存递增。
- 页面导航保留按项目隔离的未保存草稿；退出整个应用只保留已保存版本，未保存草稿不是自动存档。
- “重新载入”必须确认才丢弃草稿。保存携带预期 revision，拒绝静默覆盖更新版本；冲突时保留本地草稿。
- 重新接管在文件读取完成后获取最新项目记录，不用旧元数据覆盖读取期间保存的规划。
- 应用单实例、同步 SQLite 保存路径中检查并写入；不宣称跨进程协作或云端同步。
- 规划只在 Beaver 数据库，不随当前游戏目录复制或玩家程序导出。备份规划需要备份 Beaver 数据；规划导入导出是未来能力。
- 旧 `beaver.project.json` / `GameBrief` 的任务上下文和回退契约仍有效。新规划不会改写它，也不会修改已排队任务。未来统一两套语义必须显式迁移，不能在这次 UI 原型中悄悄执行。

## 8. 参考与可追溯性

已核对 [City Game Studio 官方翻译仓库的固定版本](https://github.com/binogure-studio/city-game-studio-i18n/blob/9a23d7a097df1f9560afbb536afb6f051ed30d38/languages/zh.yml)。原始提交为 `9a23d7a097df1f9560afbb536afb6f051ed30d38`，避免未来 master 变化让计数失真。

| 来源键 | 采用范围 |
| --- | --- |
| `LABEL_TYPE_*` | 实际类别 64 项；排除 `LABEL_TYPE_BUILDING` 这类非类别标题 |
| `LABEL_THEME_*` | 实际主题 49 项；排除 `LABEL_THEME_LIST` 等目录标题 |
| `LABEL_TARGETTED_AUDIENCE_ALL/YOUNG/MATURE` | 三个目标受众，Beaver 自行定义内容边界说明 |
| `LABEL_GAME_SIZE_INDIE/NORMAL/BIG/AAA` | 四个规模名称，Beaver 自行定义复杂度说明 |
| 三阶段、在线容量、媒体 / 试玩 / 宣传相关字段 | 借鉴交互分类；不复制经营成本、员工数值或收益公式 |

每个类别和主题的 `sourceKey` 位于 `src/shared/blueprint-catalog.ts`，显示名称按 Beaver 的通用游戏分类表述整理。未复制完整 YAML、商业游戏代码、画面、音频或美术；未核实到该翻译仓库的明确许可证，因此不以“公开仓库”等同可任意复制授权。对外商业分发前如扩大复用范围，需再核实授权。

## 9. 下一轮讨论和停止条件

本轮完成条件：真实应用能创建/接管、修改并保存草案，15 项均有清晰含义，所有新业务按钮不执行外部操作，重启可读取保存结果，默认及最小尺寸可用。

体验后优先讨论：独立优先级是否合适、分类命名与排序是否需要调整、服务器规划需要哪些额外字段、阶段格子将来怎样关联交付素材。用户未认可前不继续扩建自动制作、部署和发行后端。
