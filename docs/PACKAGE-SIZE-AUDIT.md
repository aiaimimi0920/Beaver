# 为什么 Beaver 的 EXE 有约 240 MB

## 结论

你的质疑是对的：Beaver 的业务代码没有大到需要 240 MB。体积主要来自我选用并整包分发的 Electron 桌面运行时，而不是游戏编排逻辑、AI 模型或 Godot/Blender 本体。

这是当前技术选型和打包方式带来的固定成本，不是“编排型应用必须这么大”。我之前优先推进了功能，却没有把轻量交付作为同等级约束来处理，这一点需要纠正。

## 本次实测

检查对象：`release/Beaver-0.1.19-win32-x64`。数据来自当前磁盘上的实际文件，不是框架官网的估算。

下表使用 MiB（1,048,576 字节）；Windows 文件属性通常以 MB 标签显示近似这一单位。

| 内容 | 实际体积 | 说明 |
| --- | ---: | --- |
| Beaver.exe | 234.80 MiB，246,201,856 字节 | 品牌资源替换后的 Electron 可执行文件 |
| 原始 electron.exe | 234.80 MiB，246,201,856 字节 | 与 Beaver.exe 字节数完全相同；并非 Beaver 业务把 EXE 撑大 |
| 完整发布目录 | 379.29 MiB | 用户实际需要保留的目录，比单个 EXE 更大 |
| 原始 Electron 运行时目录 | 367.56 MiB | 当前打包脚本将整个目录复制进发布包 |
| Beaver 应用目录 resources/app | 10.33 MiB | 编译产物、资源、模板、skills 等 |
| 应用目录内的 source map | 7.30 MiB | 调试映射文件，目前也随包发布 |
| 应用目录扣除 source map | 约 3.03 MiB | 更接近业务产物本身的量级，不代表可独立运行 |
| locales | 48.30 MiB | 随 Electron 一起复制的多语言资源 |
| dxcompiler.dll | 24.55 MiB | 图形运行时组件，不是 Beaver 的游戏业务代码 |
| LICENSES.chromium.html | 19.52 MiB | 第三方许可清单，不能为了减包直接不顾许可要求删除 |

应用业务与资源约占发布目录的 2.7%；其余主要是桌面运行时及配套文件。

## 为什么会这样

当前实现是 React/TypeScript 界面配 Electron 主进程。Electron 分发包含浏览器渲染引擎和相关运行能力，因此即使应用只显示少量界面，也必须承担这套运行时的体积。任务调度是否重计算，不决定这部分固定体积。

当前 `scripts/package.mjs` 的关键流程是：

1. 完整复制 `node_modules/electron/dist`。
2. 复制 Beaver 编译产物、资源和文档。
3. 替换 Electron 的图标、版本信息等品牌资源，生成 `Beaver.exe`。
4. 删除发布目录里原名称的 `electron.exe`。

因此，这个 EXE 并不是只包含编排业务的本地程序；它首先是一个完整 Electron 运行时。当前包也没有把 Godot、Blender 或本地大模型捆进去，这些不是这次体积问题的原因。

## 减小体积的两种不同层次

### 打包层清理

生产包不携带 source map、审查必要语言资源、整理开发文档，可以节省一部分空间。但语言资源需要按实际本地化和回退行为验证，许可文件也必须合规处理。

压缩安装包只能减少下载体积，解压后运行时仍然存在；把业务文件打进归档也不会消除 Electron。上述做法都不能把当前 234.80 MiB 的 EXE 变成一个真正的小型程序。

### 桌面运行时选型

如果产品明确要求小体积，就必须重新评估是否继续随应用携带整套浏览器运行时，或者改为使用系统 WebView/原生桌面宿主。这才涉及根本体积来源。

但更换宿主不只是换打包命令：当前主进程使用 Node SQLite、文件与进程控制、Codex 通信、IPC、托盘和凭据存储，这些能力都要迁移或重新接入、逐项回归。复用系统 WebView 也必须考虑干净机器上缺少运行时的情况，不能以减小安装包为由破坏“用户零环境安装”的目标。

这里没有做出未经验证的迁移后体积承诺，也没有擅自开始重写架构。本次只检查实际文件、确认原因并记录结论。

**简而言之：业务本身只有几 MiB；约 240 MB 的 EXE 是 Electron 的成本。我选用的桌面技术栈及当前全量打包方式，没有达到你预期的轻量化要求。**
