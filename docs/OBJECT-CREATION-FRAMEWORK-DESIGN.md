# 对象创作框架开发设计

日期：2026-09-16。设计版本：v0.3。状态：产品规则和 UI 已确认，新框架待实施；具体开发顺序、交付与进度统一见 [实际框架实现开发计划](FRAMEWORK-IMPLEMENTATION-PLAN.md)。本文“任务面板”和“对象创作面板”在当前 UI 分别名为“创作”和“制造”。

上一轮 Beaver 与 Codex 通用框架的完成范围见 [完成记录](WORKFLOW-FRAMEWORK-COMPLETION.md)，现行协议见 [通用框架契约](WORKFLOW-FRAMEWORK.md)。本文在其基础上设计任务面板、对象面板和对象创作面板。上一轮的测试与历史原生验收不能证明本文的新能力已经完成。

第 1 节记录用户已确认的产品规则；后续的数据名称、接口分组、迁移步骤和模块划分属于实现方案，开发时可以调整具体表达，但必须保持这些规则。与旧文档存在差异时，本文约束新框架的目标，旧文档继续说明历史实现及其证据；正在执行的旧任务保持原有协议和审批策略。

## 1. 已确认的产品规则

### 1.1 三个面板及任务层级

任务泳道展示所有正在执行的任务，包括粗修、中修和精修任务，并保留排队、等待、失败及历史查询。粗修接收宽泛目标并拆成中修任务，中修围绕一个对象组织修改并生成精修任务，精修执行具体制作步骤。三个层级都需要真实的持久任务身份、状态和关联，完成结果逐层汇总。

对象面板按对象组织内容。一个 NPR 人物对象可以包含模型、贴图、法线、材质、骨架和引擎场景；一个 UI 场景也可以包含子 UI。独立贴图、代码功能同样可以成为对象。对象面板展示全部对象，包括已完成对象、待制作对象及没有任务绑定的对象，并保留按素材格式筛选和查看文件的能力。

对象创作面板围绕任意选中的对象展示创作流程、阶段、精修任务、执行尝试、实际输入输出、版本备份和验收要求。其任务与泳道中的任务共用身份和状态。对象可以没有当前任务，创作面板仍能查看成品和历史，并发起下一次修改。

粗修、中修、精修分别表达用户介入的范围。用户从粗修入口发起任务后，系统仍须走完整的对象分解和精修执行链。用户可以查看、调整自动拆分，手动增加任务，以及在对象或具体阶段输入新的要求。对象入口允许直接创建独立中修任务，无须补造粗修父任务；从已有粗修任务派生时保留原归属。

### 1.2 对象修改与引用

同一对象同一时刻只允许一个中修任务拥有修改权。所属精修任务继承这份修改权，并在对象工作区内串行制作。暂停、等待回答和等待验收期间仍保留修改权；当前任务完成并通过对象整体验收，或明确取消且处理完工作区后，才释放给下一项。其他中修任务排队，默认开始时绑定最新已接受版本，用户也可以明确指定历史工作基准；领取时核对要求并固定实际输入。展示版本切换不影响制作，运行后改基准必须显式返工，不能覆盖已有尝试。从历史基准发布需核对当前接受版本及替换差异，不自动合并二进制内容。独立对象可并行制作。

对象的自有组件随对象统一修改、版本化和验收。引用的独立对象拥有自己的身份、队列和历史。例如教室中的椅子数量与摆放属于教室修改，椅子网格属于椅子对象修改。界面必须区分自有内容和独立引用。

对象引用固定到具体的已接受版本。椅子有新版本时，现有教室显示“可更新”，不会静默替换。更新引用需要明确的修改任务和相关检查；历史版本继续引用原版本，以便复现。

### 1.3 预览、反馈和验收

每个对象及其创作面板都有预览位置，用于显示对象的实际效果，并支持文字、框选标注和适用的局部选择。可视对象使用真实模型、贴图、UI 或运行结果；对象面板默认展示已接受版本，制作中结果明确标注，创作面板展示当前制作状态。没有可用内容时显示待制作或预览缺失，不能生成一张示意美术图冒充实物效果。

用户可以放大、切换适用视角并提交修改。反馈绑定提交时的对象、版本或执行尝试、实际截图及视角。排队后内容发生变化时，重新解释旧反馈，不把旧屏幕坐标直接用于新模型。代码等非可视对象优先显示关联的真实运行或验证画面并注明来源；没有这种画面时使用类型和状态占位，继续提供提示词和创作入口。

新工作流允许配置验收策略：普通精修步骤在相关检查通过后自动推进，关键方向或质量阶段需要人工批准，中修任务最终需要对象整体确认。用户可以在任意阶段暂停和介入。程序检查、AI 评价与用户批准分别记录，技术失败不能靠人工批准绕过。旧交付工作流的逐阶段 owner 审批在显式迁移前保持有效。

### 1.4 对象导入与项目存储

对象导入支持多文件/多文件夹、已添加到 Beaver 的项目对象、未添加但具有 Beaver 项目结构的外部项目对象。后两种方式共用对象读取和选择逻辑，第三方来源无需先登记整个项目。新建项目在根目录创建 `.beaver/`，项目的 Beaver 管理信息统一保存在其中，完整项目可独立提供对象信息。

具体规则、建议目录、现有存储差异及后续验证见 [对象导入与项目 .beaver 存储规范](OBJECT-IMPORT-AND-PROJECT-STORAGE.md)。该补充约束后续实现，当前 UI 继续使用 mock 数据。

## 2. 全链路示例与面板职责

以“让一个 NPR 人物在教室里跳舞”为例，粗修任务需要识别人物、教室和最终表演场景等对象，以及动作和控制逻辑的归属。动作是否属于人物自有内容或独立可复用对象，由需求决定并记录；不能只做出人物和教室就宣布整个目标完成。

```text
粗修 T0：人物在教室跳舞
  中修 T1：制作人物 O1
    精修 T1.1、T1.2 ...：按 O1 的线性阶段制作和检查
  中修 T2：制作教室 O2
    精修 T2.1、T2.2 ...：按 O2 的线性阶段制作和检查
  中修 T3：制作表演场景 O3，依赖 T1、T2 的已接受结果
    精修 T3.1 ...：固定引用 O1@v1、O2@v1，配置动作和相关运行逻辑
    精修 T3.n：检查实际场景与目标要求
  汇总：所需对象均已接受，场景满足 T0 的验收要求
```

T1 与 T2 没有其他冲突时可并行；T3 的制作必须等待它实际依赖的版本可用。每个对象的阶段保持线性。粗修的对象依赖可以形成无环图，不要求所有独立对象全局排成一条线。

任务面板提供层级展开、对象筛选、当前阶段、执行者、等待原因和相关入口。默认展示所有活动任务；折叠时仍显示活动子任务数量和阻塞摘要，展开后能定位每个精修任务。历史任务可筛选查询，不能因界面折叠而改变调度状态。

对象面板提供语义分类、缩略图、自有组件树、引用对象树、已接受版本、当前修改者和排队任务。文件类型作为辅助过滤条件保留。一个纹理作为人物自有内容时可在人物内查看；若被登记为独立对象，则具有独立修改入口和被引用关系。

创作面板默认以 `objectId` 打开，选择当前或历史制作轮次，再查看具体阶段和尝试。没有活动轮次时展示已接受结果和“开始修改”；初始空对象展示制作入口。多个窗口查看同一对象只建立多个观察订阅，业务执行仍由同一任务系统管理。

## 3. 领域身份和唯一状态来源

以下名称均为拟定契约，不代表已有字段或 API。优先扩展现有任务和文件存储能力，按职责增加强类型记录，避免把所有对象信息塞进一个无约束 JSON 字段。

| 记录                   | 最少需要表达的信息                                                             | 归属和约束                                                   |
| ---------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------ |
| `Task`                 | ID、项目、粗/中/精粒度、父任务、依赖、目标、验收要求、计划版本、状态及阻塞原因 | 所有任务面板共用；粒度独立于现有 direction 和 capability     |
| `ObjectRecord`         | 稳定 ID、项目、名称、语义类型、生命周期、已接受版本指针                        | 无任务也能存在；新对象允许没有已接受版本                     |
| `ObjectComponent`      | 稳定组件 ID、所属对象、角色、内容映射                                          | 对象内部的内容；统一写入权，无独立对象发布版本               |
| `ObjectReference`      | 引用 ID、来源对象版本、目标对象 ID 与版本、实例参数                            | 固定已接受版本；摆放等实例参数属于来源对象                   |
| `ObjectVersion`        | 不可变清单、内容哈希、自有组件、固定引用、来源轮次、验收与预览                 | ID 与对象内版本序号分开；只有接受的版本可被正常下游消费      |
| `ProductionRun`        | 对象 ID、中修任务 ID、基准版本、需求/模板版本、工作区、当前阶段                | 一个中修任务对应一轮对象修改；重试和阶段返工保留在本轮历史中 |
| `Stage`                | 轮次、稳定 ID、顺序、要求、精修任务、候选及批准记录                            | 制作与验收边界；状态由任务和当前有效回执共同决定             |
| `Attempt`              | 精修任务、输入快照、执行身份、检查点、实际工具事件、输出和结果                 | 一次执行；重试使用新 ID，不覆写旧证据                        |
| `ObjectQueueEntry`     | 对象、中修任务、请求顺序、调度顺序、等待原因                                   | 一任务一有效队列项；同对象只能有一个活动修改者               |
| `Preview` / `Feedback` | 对象与内容版本、预览来源、图片哈希、视角、选择、提示词和处理状态               | 预览身份独立于任务状态；反馈可追溯到实际看见的内容           |

任务父子关系表示责任与完成汇总；`dependsOn` 表示执行依赖，两者分别保存。一个子任务只有一个责任父任务；被多个目标使用的对象通过版本引用或依赖关联，不能把同一个修改任务挂成多个父任务的可变子任务。独立中修任务的父任务可以为空。

中修任务绑定一个可写目标对象；需要修改多个独立对象时拆成多个中修任务。精修任务必须属于一个中修任务，并继承相同的对象与轮次。用户在创作面板手动增加精修任务时，若没有当前轮次，由 Beaver 原子创建中修任务、队列项和精修任务；若选中已有轮次则明确加入该轮。粗修和中修可以运行只读规划或需求澄清，但实际产物修改登记到精修任务。

阶段、执行尝试和工具调用不会自动生成新的任务卡片。阶段可以包含多个精修任务；一个精修任务可以有多个尝试；尝试可以使用多个 Skill 和工具。具体插件调用是执行证据，只有具有独立目标、恢复意义或验收要求的工作才拆成精修任务。

`AssetPick.objectId` 当前表达 Blender 场景对象身份，不能直接复用为 Beaver 的 `ObjectRecord.id`。需要在产物或会话映射中记录场景对象、实例与所属对象/组件/引用的关系；无法映射时保留几何线索并澄清目标。

对象内容版本、任务计划 revision、工作流配置 revision、场景 revision、视角 revision 和协议版本分别管理。对象版本序号不使用应用版本号；应用内部四段版本、对外三段版本规则继续见 [版本约定](VERSIONING.md)。

## 4. 对象队列、工作区和发布边界

### 4.1 写入权与排队

中修任务入队前即可保存目标和澄清记录，但不能预先复制一个未来要写的旧基准。默认保持提交顺序；人工可调整尚未开始的任务顺序并记录原因，不抢占当前修改者。依赖尚未满足的队首显示具体阻塞，后项不静默越过它；修改顺序同时复核依赖无环和任务资格。

调度器先确认依赖和运行资格，再以对象级事务领取写入权，解析默认最新或显式指定的已接受基准，记录当前接受版本作为发布比较点，创建本轮工作区并固定输入。队列领取、基准绑定和调度回执必须幂等；文件准备在数据库锁外完成，提交时重新核验对象版本和领取身份。准备失败保留明确的恢复记录，不留下可被误用的活动执行权。

每次领取或恢复执行使用递增的写入代次，回调除 task / thread / turn 外还须核验对象、轮次和代次。单一中修拥有者下面同时只激活一个可写精修 attempt；中修协调器和精修执行者不能各自启动一个场景写入者。等待子任务和等待审批不占用运行中的 Codex 槽位，逻辑写入权仍保留。

同轮精修按阶段及计划中的任务顺序交接。前一精修停止写入后，冻结输出检查点，完成当前要求的检查、反馈处置和该精修自身的批准门槛，才允许下一精修启动；下一精修固定此前有效检查点及引用作为输入，在同一工作区继续。阶段整体批准位于本阶段所需精修完成之后，控制下一阶段。失败、中断或待批准的精修阻止后继写入；返工前停止后继执行、保存现场并恢复到选定检查点，已受影响的后继结果失效。

队列中的后续任务开始时由 Codex 比较当前版本与最初要求。如果前项已实现目标，记录验证依据后提出无需修改的完成结果；若前项改变了假设，更新计划并按重要性追问。既有已确认设计不可静默覆盖，旧参考图也不能直接转成新版本上的坐标操作。

其他任务可以读取已接受版本；工作区和未接受候选默认不作为下游正式输入。预览可以展示制作中结果，但必须标识来源。多个对象并行不等于允许多个任务写同一共享文件或同一 Blender/Godot 场景。

### 4.2 工作区与文件归属

每轮对象修改使用一个工作区，所属精修任务共享这个工作区及其受管场景。阶段切换与精修重试建立检查点，不复制独立工作副本再合并 `.blend` 或图片。下一轮从领取时解析并固定的已接受基准清单重新建立工作区。无须为每个精修任务创建 Git worktree。

受管 Blender/Godot 会话绑定当前轮次及工作区。不同对象并行时使用隔离的可写会话；工具只支持单一场景时，将该工具作为串行资源调度并展示等待原因，不能把两个对象任务同时接到同一个可变场景。只读预览与制作共用会话时也需协调冻结和读取时机。

对象清单区分自有可写文件、引用对象的只读版本输入、预览和检查报告。一个可写文件只能有一个对象所有者；相同 blob 可按哈希去重存储，但内容相同不授予另一对象对原路径的写权限。已有单个 `.blend` 内混有多个待独立编辑对象时，先登记为同一组合对象，或在明确的结构调整任务中拆分；不能给两个对象都登记同一个可写文件。

项目主场景、共享代码和资源配置需要明确所有者，可以归入场景或项目配置对象。需要改变其内容的任务进入该对象队列。独立对象任务只能输出自己的文件和清单，跨对象组装由相应的场景/集成中修任务处理。代码对象同样遵守写入权；不能用普通代码任务绕过对象文件归属。

引擎导入缓存、临时渲染及验证数据放在工作区隔离目录，不回写引用的冻结版本。记录逻辑所有权并核验写入范围只能限制 Beaver 管理的流程，当前可信外部工具仍有本机用户权限；发现应用外修改时标记漂移并阻止发布，不能宣称已获得操作系统级隔离。

### 4.3 阶段备份、版本与项目物化

重大修改前建立可恢复检查点，每次阶段提交冻结候选清单、实际文件和相关报告。阶段验收通过仅解锁本轮下一阶段；对象面板默认版本保持不变，直到中修的整体验收和发布完成。文件备份使用已有内容寻址存储，不要求每阶段重复保存全部相同字节。

用户可以查看和导出历史输入、阶段候选及接受版本。当前轮次回到旧阶段时创建新尝试，失效受影响的下游结果；已经接受的对象要求回到旧版时，创建排队的恢复任务并发布一个新版本，保留被恢复版本的来源。独立试做方案创建新的对象变体和队列，记录来源对象版本，避免同一对象同时存在多个可写分支。

发布需要核验最终候选、需求/配置版本、引用闭包、必需检查、人工决定和反馈处理结果。文件系统与 SQLite 不能假设为一次原子写入：先冻结和验证内容，写入发布准备记录，再通过可恢复文件日志物化到项目，最后原子更新对象接受版本、任务结果和队列释放记录。读者只能看到已提交版本；物化未完成时阻止依赖该项目快照的执行，恢复优先完成或回退该记录。

同一项目的短时物化提交和项目快照读取需要协调，防止把不同对象的半次提交拼成一个输入快照；它不限制不同对象在各自工作区内并行制作。已运行任务继续使用其冻结输入，接受新版本不能修改已开始 attempt 的输入文件。

应用外并发编辑造成冲突时，保持原接受版本和对象修改权，展示待处理状态，禁止强行覆盖或自动合并二进制产物。没有内容变化的修改可以在确认目标已满足后引用原接受版本完成，并保留本轮证据，无须制造一个空内容版本。

### 4.4 暂停、取消和恢复

- 暂停、等待回答、阶段或对象待批准：停止派发新的制作动作，保留中修修改权；允许观察和读取证据。
- 精修失败或中断：本轮保留现场，待核验后以新 attempt 恢复；失败不能使后续阶段或队列项自动开始。
- 中修取消：先阻止新写入、停止本轮拥有的执行并确认停止，冻结或处理未发布内容，再关闭轮次和释放队列。已接受版本不受未发布结果影响。
- 粗修暂停或取消：作用于它拥有的中修子任务，分别执行上述流程；不取消其他粗修或独立任务，只因它们使用同一对象版本就连带取消是不允许的。
- 宿主崩溃或重启：活动执行记为中断，写入权进入待恢复状态；不按超时自动发给下一项，不自动恢复模型消耗。先核验进程、场景、发布日志和已发生副作用，再显式继续或取消。

写入权是持久责任，进程和会话是可替换的执行资源。迟到回调只能补充历史，不得变更新执行。取消不能保证撤销已发生的外部副作用；对“再拉长一点”等操作沿用待核验恢复语义，不因重试重复修改。

重启后由 Beaver 恢复服务扫描持久记录，在对象和任务入口向 owner 提供核验、继续及取消操作，不依赖原 Codex 会话仍然存在。一次核验复用持久 operation，以当前对象/轮次 revision 和恢复代次原子领取；重复请求返回同一回执，并发请求不能启动第二个核验或执行者。核验结果区分可继续、可取消和冲突待处理；owner 的继续/取消绑定该结果及代次，核验失败保留待处理状态。停止确认和工作区处理完成后才能取消释放，不能用“强制完成”解除未确认的外部写入。

## 5. 拆分、人工介入和完成汇总

### 5.1 自动拆分与需求补充

Beaver 将用户目标、已有对象版本、已回答问题、自动强度和验收要求交给 Codex。Codex 给出可登记的对象划分、中修任务和依赖，再在每个对象轮次内提出线性阶段和精修任务。Beaver 校验归属、依赖、写入范围及策略，将任务和计划 revision 原子落库后交由统一调度器执行。

“我想要一个二次元美少女”这类不完整目标允许自动补充低成本、可撤销细节，并保存采用的假设、依据及决策来源。用途、风格方向或影响大量返工的选择按照既有 `askRatio` 和提问机制处理。已确认的需求作为版本化输入传给后续任务，避免反复提问或无记录改动。

中修可以先登记对象和任务草案，精修可以按当前阶段逐步细化，无须一次猜出全部工具操作。但计划必须明确尚未展开的阶段或要求；“当前精修列表为空”不能推导为对象已完成。支持任意阶段内的多个精修任务，不把 NPR 固定写入核心枚举。

### 5.2 人工调整计划

用户和 Codex 都通过同一业务操作提议增补或修改计划。用户可以编辑未开始任务的目标、验收规格、依赖和顺序，手工增添对象任务或精修任务；界面显示变更前后、影响范围及采用者。AI 的建议不直接覆盖用户决定。

变更需要携带预期计划 revision。已运行任务的定义固定在 attempt 快照中，新要求以反馈或计划修订保存，到安全切换点应用；不改写正在执行的历史输入。不允许通过改父任务、改对象 ID 或换轮次绕过队列。尚未开始任务可以撤回，已有历史的任务保留取消记录。

调整已通过阶段时，先确定受影响任务、候选及引用，暂停相关执行，再创建返工尝试并使后续依赖结果失效。新的计划应展示需要重做或重新检查的部分，未受影响的证据保留；只有实际输入和验收依赖仍一致时才能复用。阶段结构变更采用新的模板/计划版本，旧批准不能无条件转到新结构。

依赖图同时核验任务依赖、阶段顺序和对象队列先后关系。禁止环路和跨对象嵌套领取后等待另一把写入权。运行中新增的要求若必须由排在当前任务之后的同对象任务完成，应改为当前轮次内精修，或明确结束/取消本轮后重新排队；不能一边持有对象一边等待它的后继任务。需要其他对象修改时先提出其任务和依赖，检查有无循环等待，再安排当前轮次的安全等待或重新计划。

### 5.3 任务完成与验收语义

执行已结束、检查通过、阶段已接受、对象已发布、粗修目标已完成分别记录。推荐保留任务执行状态与当前验收状态两个维度，阶段和面板读取这些记录的业务投影，不建立可以自行推进的第二份 UI 状态。

精修完成要求当前定义对应的输出和必需检查有效，且相关反馈已有结果；需要人工门槛的结果处于待批准。阶段推进要求本阶段所需精修全部达标、阶段候选通过配置门槛，才释放下一阶段。中修完成要求全部必要阶段通过、最终对象满足规格、对象整体获得人工确认，且发布已提交。

粗修完成要求当前计划的必要中修任务全部完成并得到接受结果，同时整体场景或集成目标的验收成立。任务没有子项、某个 Codex turn 结束、所有子项都被取消，均不能自动说明目标已实现。取消必要任务须同步修订目标/验收并记录决定，否则父任务保持未完成。

后续独立中修修改对象时，已完成粗修的历史结果仍固定到当时版本。需要让已交付场景采用新版时创建关联更新任务；不能将历史粗修悄悄恢复执行并替换其证据。

新工作流冻结本轮验收策略：普通步骤可在有效检查后由策略接受，关键阶段需要 owner 决定，对象最终需要 owner 确认。自动接受记录策略身份和版本，不能冒充用户批准；人工和模型评价分开保存。策略变更对已有候选的影响须显式处理，技术失败、过期检查和未解决反馈均不能绕过。

现有 `deliveryPlan` 的逐阶段 owner 策略以及历史普通任务的 `autoAccept` 继续按原规则读取。新对象任务的自动推进需由新契约显式启用，不通过全局修改 `autoAccept` 放开旧阶段门槛，也不由 Codex 自行降低标准。

## 6. 实际预览、反馈和双向导航

### 6.1 预览来源与刷新

对象卡片和创作面板共用预览记录，各自选择显示接受版本或制作中候选。预览记录至少包含对象 ID、对象版本或轮次/attempt/候选 ID、内容哈希、生成时间、渲染工具与插件版本、画面尺寸、视角和来源类型。以这些信息建立缓存身份，不能只用文件路径、文件时间或对象名称判断缓存有效。

可视内容通过对应工具生成实际画面：模型使用真实场景渲染，贴图显示实际图片，UI 使用实际布局或引擎运行画面。代码对象关联运行场景时标明场景版本、代码版本及展示范围；同一张游戏截图可以关联多个对象，但不能据此宣称所有对象的行为已验证。验收证据与普通缩略图分开标记。

保存、候选提交、发布、受管场景变化和用户主动刷新触发预览更新；合并短时间内的连续请求，后台按资源预算渲染。缩略图刷新不必启动一次新的 AI 推理。卡片显示“已接受”“制作中”“更新中”“内容已变化”“预览不可用”等来源或状态；更新时间和渲染失败原因可查询。没有稳定映射或无法渲染时保留占位和文字操作，禁止把旧图当作当前实际效果。

预览请求捕获对象及版本身份。对象切换、轮次切换或请求被更新后，迟到结果只能缓存到原对象，不得覆盖当前选中对象的画面。创作面板可以实时观察受管会话；进入标注时冻结确切画面，随后场景继续变化也不能替换这张参考图。

### 6.2 选择与反馈

反馈保存提示词、原始冻结图及哈希、显示的对象与版本、组件或引用线索、相机和投影、场景/视角 revision，以及框选、箭头、笔刷或拾取结果。屏幕坐标先去除留白和缩放偏移，再换算为图片坐标；记录原始图像尺寸，正确处理 DPI。二维框选只是所见区域，不能声称已准确选择三维背面或全部几何。

Blender 对象名、网格索引、Godot 节点路径和拾取 ID 都是指定产物版本或会话下的定位线索。拓扑、实例和场景改变后，需要重新映射与核验；无法确认时向用户展示原图与当前结果并澄清，不能直接重放旧索引或坐标。

在场景中选择人物或椅子时，先判断修改范围：位置、数量和实例参数归场景对象；模型或贴图内容归被引用对象；只想改变此实例的独立外观时，可以创建源版本派生的新对象并更新该场景引用。涉及多个独立对象的意图拆为各自中修任务及依赖，保持单对象写入规则。

反馈提交时明确采用以下一种处理方式，界面展示归属与预期时机：

- 加入当前对象轮次：登记为待处理反馈，在可停止的工具边界应用，必要时新增精修任务、修订计划或返工。不能只把文字追加到会话却不登记任务影响。
- 作为后续修改：创建独立中修任务并进入对象队列，绑定原参考证据；开始时根据新基准重新解释。没有当前轮次时采用此方式。

反馈使用稳定请求 ID 去重，记录提出、待澄清、已采纳、已处理、明确拒绝或转交后续任务的状态与原因。提交到当前轮次的反馈在有明确处置前阻止其影响范围的验收；处置结果包括修改已完成且具有当前有效证据、owner 确认拒绝或无需修改、owner 确认转交后续任务。待澄清和仅已采纳均不算处理完成，AI 不能自行将反馈标为“不必要”来跳过。转交后的反馈有明确的后续任务 ID，当前轮次由 owner 确认其验收范围变化；直接提交为后续中修的反馈不阻塞当前轮次。

反馈提交与对象发布可能同时发生，服务端以预期轮次、计划 revision 和当前状态作并发校验。若轮次已提交或关闭，返回冲突并要求重新选择后续任务，保留反馈草稿和截图；不把“修改当前轮次”静默转换成新任务，也不丢失用户输入。历史结果允许标注和发起新修改，历史内容及批准记录保持只读。

### 6.3 双向导航

持久关联支持 `任务 -> 对象 -> 制作轮次 -> 阶段 -> 精修任务/attempt -> 候选/接受版本 -> 文件` 的正向查看与反向追踪。入口携带项目、对象及可选的任务、轮次、阶段、版本身份，打开后高亮目标；任务删除展示和对象改名不能破坏既有稳定 ID。

从模型、贴图、场景或预览返回时，先定位所属对象和来源版本，再提供“制作它的任务”“当前修改任务”“相关引用任务”等入口。一个文件或 blob 可能有多个只读消费者，界面区分内容所有者与引用者，不能随意选一个任务作为唯一来源。缺少历史来源时显示未登记或历史信息不足，允许补充归属，不伪造制作记录。

无活动任务的对象可以直接打开创作面板查看版本并发起修改。从精修卡片进入面板时选中对应轮次和阶段；从对象卡片进入时默认选当前轮次，没有活动轮次则显示接受版本。任务泳道、对象面板和多个创作窗口订阅相同业务事件，不能分别维护可写的进度副本。

## 7. Beaver、Codex、Skills 与插件的职责

### 7.1 统一控制与可观察执行

Beaver 核心负责对象登记、任务关系、队列、版本、工作区、策略核验、交付、恢复和事件持久化。桌面、HTTP、MCP 和动态任务工具调用同一业务服务。Codex 负责理解、拆分、补充和追问、选择工具、执行当前授权范围内的精修、解释检查结果并提出返工方案。

Beaver 可以启动或继续 Codex 执行；Codex 可以通过受管工具回调 Beaver，读取输入、提出任务与计划、请求插件操作、提交输出和证据、请求澄清或后续动作。回调提出的动作经 Beaver 核验后落库，由调度器决定何时执行；不能在一次回调中另起一套自主调度链绕过对象队列。

实际输入输出包括冻结文件、固定引用、有效需求与验收策略、Skill/插件版本、工具操作及其结果、候选和检查报告。界面可以展示传入的 Skill、模型声明正在使用的 Skill，以及可观测的实际工具事件，并分别标注来源。仅向模型提供 Skill 文本不能证明执行了它；不能声称获取了模型未公开的内部推理过程。

### 7.2 拟扩展的业务操作

下表仅给出未来操作分组，最终方法名和协议版本由实现确定，当前不代表任何 API 已注册或可以调用。优先扩展现有 `beaver_task`、`beaver_workflow` 及核心服务，避免为新面板复制传输层和状态机。

| 操作分组       | 目标                                            | 必须校验的边界                                    |
| -------------- | ----------------------------------------------- | ------------------------------------------------- |
| 对象查询与登记 | 创建空对象、登记组件/引用、读取接受版本和历史   | 项目隔离、文件归属、版本存在及可引用状态          |
| 拆分与计划修订 | 提交粗/中/精任务及依赖、编辑或撤回未开始项      | 责任父任务、计划 revision、线性阶段、队列依赖无环 |
| 排队与执行     | 提交中修、调整未开始队列、暂停、恢复和取消      | 当前拥有者、写入代次、执行身份、停止与恢复回执    |
| 阶段与对象交付 | 提交候选、运行检查、请求批准、发布版本          | 冻结输入输出、策略和检查版本、批准权限、发布日志  |
| 预览与反馈     | 请求预览、冻结视图、提交标注、采纳或转交反馈    | 实际画面来源、内容版本、请求去重、轮次是否已关闭  |
| 事件与追溯     | 查询任务/对象关系、执行轨迹、操作结果与历史文件 | 查询范围、稳定游标、事件顺序、脱敏与文件导出边界  |

写操作携带稳定请求 ID 和预期 revision；执行中的操作还绑定对象、轮次、精修任务、attempt、写入代次及受管会话身份。身份从宿主已认证的调用上下文得到，不能信任模型任意填写的 owner 字段。事务冲突返回当前 revision 和可恢复原因；相同请求的重复提交返回原回执，不重复排队、安装、建任务或发布。

耗时的场景读取、预览、插件安装、检查和发布准备复用持久 operation，支持状态查询、取消和中断恢复，不在数据库事务内等外部进程。关键任务变化和事件在同一提交边界持久化，重连先取快照再按游标补事件；前端遇到间隙重新同步。事件可以重复送达，消费者按事件 ID 去重。

owner 批准、计划变更确认和验收策略修改保留权限区分。模型只能提交评价、候选和申请；由明确配置策略执行的自动接受记录策略身份。各入口必须执行相同的角色和内容校验，MCP 不能成为越过 UI 审批的捷径。

### 7.3 Skills 和插件使用

合适的 Godot 插件、Codex 插件和 Blender 插件优先于重复手工操作或临时编写替代工具。选择时核对任务适配性、版本兼容、实际可调用入口、许可条件和输出能力；记录选择依据与固定版本。没有合适插件时允许使用原生工具或脚本，不为追求插件使用率引入额外依赖。

工作流和精修定义声明需要的能力，执行前检测当前环境，再通过现有生命周期适配协议安装、启用、验证和调用。可自动处理的准备操作自动执行；涉及付费授权、凭据、必须重启的受管应用或不可安全继续的失败时记录明确的等待原因。共享安装位置的修改串行化，执行中的插件版本不可被另一对象任务偷偷替换。影响多个活动会话的升级应延后或使用隔离环境。

Skill 指导 Codex 完成步骤，Beaver 保存模板/Skill 标识、版本或内容摘要、使用输入及可观测结果；关键的线性顺序、写入权和批准规则由服务端执行。Skill 可以指导调用 Blender，Blender 可以调用已安装插件，相关事件和输出仍关联当前 attempt。具体 NPR 小阶段内容、插件名单和专用适配脚本在本框架之后分别迭代。

## 9. 迁移与兼容边界

### 9.1 旧数据与协议

先按 [数据迁移约定](DATA-MIGRATION.md) 备份数据库、配置、工作区和被引用的内容存储，验证备份清单和恢复路径，再引入可版本识别的对象记录及关联字段。迁移有稳定 ID 映射、状态和完成标记，重复执行不能生成重复对象、任务或版本。数据库结构升级与业务任务转换分开：前者可以保留原任务语义，后者必须显式选择转换对象并验证结果。

正在执行的旧任务继续按其协议、工作副本和审批策略运行；停止并处理现场后才允许转换。需要旧版客户端协作时，只暴露它支持的旧记录；旧客户端不得写新对象轮次。应用降级遇到不支持的 schema 或新数据时拒绝写入并提示恢复备份，不能用丢字段的解析再覆盖存储。恢复备份会放弃备份后的新写入，应先导出并由用户确认，不能把回滚描述为无损自动切换。

旧 `asset_work` 子任务转成真实精修任务时，持久记录旧 task/subtask/attempt 到新身份的映射，保留输入、候选、批准和线程来源。完成转换的工作流只有统一任务记录可以改状态，旧嵌入列表仅作为历史证据或兼容投影；不同时运行两份调度器，也不长期双写两个可变任务列表。

普通历史任务不强行套上粗修、中修、精修粒度。先识别可转换范围；未转换的任务继续以历史任务方式查看。新执行入口统一遵守对象文件归属，存在旧任务的未决写入范围时先完成或停止旧任务，再将相关内容交给新对象队列。

### 9.2 文件归组和旧入口

现有文件可由用户选择组合为对象，或由 Codex 给出归组建议再按已确认规则落库。文件后缀、同目录、名字相近和截图相似都不能单独证明它们属于同一对象，也不能证明原成果已通过对象验收。显式区分自有组件、独立对象引用和暂未归组文件，检查路径所有权及引用闭包。

历史导入保留原文件和来源，标明“已导入、待验证”等状态。创建可供后续修改的基准时冻结其清单，并完成所需检查及 owner 接受；此前不将导入状态伪装为本框架已验收的发布版本。共享输入保持固定只读引用；需要独立修改时复制成新对象并记录来源，不能偷偷转移原对象所有权。

对象面板接入后，旧素材入口仍能定位到文件及已登记对象；未归组文件保留登记入口。旧任务窗口链接通过持久映射打开对应对象轮次，无法映射时打开历史只读视图并说明原因。迁移完成并验证旧入口后，移除被替代的写路径及死字段；只为仍需读取的历史协议保留有范围的兼容代码。

对象默认归档而非立即删除。被接受版本、活动任务、反馈和引用使用的内容继续保留；涉及物理清理的策略另行确认和实现，本轮不以清理为由破坏历史回溯或迁移备份。

### 10.2 必需的行为场景

这些场景按所属批次运行，完成后登记用例、命令和证据路径，不要求每批重跑所有场景：

1. 两个任务同时修改同一图片对象：只有一个中修取得修改权；第二项在第一项接受后开始，输入为新的接受版本，任何操作不合并图片分支。
2. 两个独立对象同时制作：资源允许时并行；同轮精修共享正确现场，不能改对方文件或引用的冻结版本。
3. 当前对象等待回答、验收或进程重启：后项保持排队，执行资源可让给独立对象；旧执行的迟到回调不能改变新状态。
4. 当前轮次回到旧阶段：相关下游结果和批准失效，历史可查；排队恢复旧接受版本会产生新的接受记录，引用它的场景不会静默更新。
5. 人工增删计划、取消必要子任务或改变验收规格：粗修结果反映真实未完成项；旧批准不能被新计划自动继承。
6. 用户在旧预览上框选，或提交过程中对象/轮次被切换：反馈保留原画面来源和意图；过期定位不能写到当前另一个对象，发布竞态有明确回执。
7. 对象没有活动任务或没有可视预览：对象面板仍可见，创作面板可以查询历史和创建中修，非可视对象使用诚实的来源说明或占位。
8. 数据迁移中断后再次运行：身份和版本不重复，原文件、历史批准和任务来源保留；恢复失败不能标记迁移完成。

### 10.3 检查范围与证据要求

日常开发只运行改动相关的功能测试及必要编译/类型检查，并执行仓库官方格式检查和 `npm run check:effective-lines`；不为局部修改启动全量测试或完整游戏制作。测试通过后，只有出现新改动、失败或仍未解决的问题时才扩大范围或重复运行。全流程测试留到正式对外发布，或用户明确要求时执行。

Rust 行为改动至少完成最小编译验证并运行相关测试；UI 状态用有实际输入输出意义的交互用例验证，涉及原生窗口、环境或插件能力时再进行对应运行核验。模拟执行器可以验证框架契约，但不能作为真实 Codex/Blender 工具链成功的证据。记录缺少的真实验证，不靠扩大无关测试代替。

需要启动原生程序时遵守仓库 `AGENTS.md`：使用 `scripts/start-fresh-native-test.ps1`，新编译时传 `-Build`，先结束旧 Beaver 实例、确认选定可执行文件，每个主要验收轮次使用新建空白 Godot 项目并保留证明。游戏创作验收只走 Beaver API，不绕过应用直接调用 Codex、Godot 或 Blender 帮助它完成任务，不按名称终止无关应用。框架批次采用与本次能力对应的最小场景，无须提前制作完整 NPR 人物。

Windows 原生 Cargo 编译和测试使用同一正常 PowerShell/MSVC 环境并保留 `LIB`，日志保存后再用分析工具归纳；不切换到缺少环境变量的沙箱重跑。改动规模与交付阶段决定是否编译应用，文档修改不递增应用版本、不重打包。
