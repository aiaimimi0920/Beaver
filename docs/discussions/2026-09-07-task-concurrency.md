# 多任务并行与冲突处理：讨论稿

状态：待确认的产品与技术方案。只记录讨论，不修改应用实现。

## 先说结论

**有成熟的基础机制可以组合成可流程化的方案，但没有一种工具能保证所有游戏逻辑冲突都自动解决。**

我建议 Beaver 采用：

> **任务隔离执行 → 结果排队集成 → 三方比较 → 必要时由 Codex 适配 → 验证组合结果 → 安全写入 → 留下可回退记录。**

允许多个任务同时做事，不允许它们直接同时改同一份正式项目。Beaver 管理版本、写入与恢复，Codex 判断如何完成目标、如何适配其他任务的改动。这不违背“Codex 是黑箱”的定位：我们不编排其内部开发过程，但必须控制成果进入用户项目的边界。

标准分类有利于存储和检索，却不能代替并发控制。即使文件分得很好，两个任务依旧可能同时修改同一个人物、场景或公共脚本。

## 1. 以你说的两个对话为例

假设原项目版本为 V10，里面有 `a.gd`。

- 对话 A 的目标：增加自动存档。
- 对话 B 的目标：增加读取存档界面。
- 两个目标都需要修改 `a.gd`。

我们不让 A、B 共用项目目录，而是各自拿到从 V10 创建的完整工作副本。

```text
正式项目 V10
  ├─ 任务 A 副本：修改 a.gd，增加自动存档
  └─ 任务 B 副本：修改 a.gd，增加读取界面

A 完成 → 在候选版本验证 → 合入正式项目 V11
B 完成 → 对比 V10、V11、B 的成果
       → 将 B 的目标适配到 V11，而不是拿 B 覆盖 V11
       → 同时验证自动存档与读取界面 → 合入 V12
```

如果 B 的成果已经能与 A 正确共存，就自动合入。如果需要调整，由 Codex 在另一个候选副本中调整。如果两个目标本身矛盾，例如 A 要删除存档功能、B 要完善存档功能，就保留成果并询问用户取舍，不能由“谁最后保存”决定。

隔离单位是一次任务及其执行尝试，不是聊天窗口。暂停、重启和继续执行后，旧任务也不能绕过合入检查直接写回正式项目。

## 2. 一套明确的处理流程

### 第一步：冻结起点，创建任务副本

为每个任务记录开始时的项目版本、目标、限制和文件快照，然后创建独立可写副本。Codex、Godot、Blender 和 MCP 都面向这个副本工作。

副本包含可独立运行和验证游戏所需的项目内容，不是只复制预计会修改的一个脚本。这样 Codex 仍可自行检索、修改和验证，不需要 Beaver 预先判断它会改哪些文件。

正在运行的任务默认看到一致的起点，不把其他任务的半成品实时混进去。确实需要新结果时，在明确的检查点更新基线或创建新执行尝试，并让 Codex 重新适配。

### 第二步：冻结成果，而不是边写边合

任务提交成果时，应停止或隔离继续写入该成果的子进程，生成不可变的成果快照与实际变更清单。不能只相信 Codex 口头报告“改了哪些文件”。

任务成果、生成素材、日志和后续集成尝试都保留关联关系。一个任务可以多次尝试，但已冻结的旧成果不被新尝试覆盖。

### 第三步：进入项目的集成队列

同项目一次只发布一份新的正式版本。多个任务的生成、编写和测试仍可并行。

每个待集成成果都要基于当时最新的正式版本构造候选项目。不是“两个任务分别测试通过，因此随便合在一起也通过”。GitHub 的合并队列采用的也是将变更与最新目标分支、队列中在前的变更组合后再运行检查的思路；这里借鉴机制，不要求用户使用 GitHub。[官方合并队列说明](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)

### 第四步：三方比较，分级处理

三方是：**任务起点、当前正式项目、任务成果**。这是判断双方分别改变了什么的基础，不是简单比较最后修改时间。Git 的三方合并也保留共同祖先和两侧版本供比较。[Git 合并说明](https://git-scm.com/docs/git-merge)

| 情况                                         | 默认处理                                             |
| -------------------------------------------- | ---------------------------------------------------- |
| 当前正式文件没有偏离任务起点                 | 将任务变更放进候选项目，进入验证                     |
| 双方产生完全相同的内容                       | 作为已满足的变更处理，不重复覆盖                     |
| 同一文本文件的独立改动                       | 尝试三方合并，然后验证，不直接宣布成功               |
| 同一段内容、删除与修改、重命名与引用发生冲突 | 给 Codex 完整三方资料与原始目标，在候选项目适配      |
| 改动不在同一文件，但接口或设定不兼容         | 由组合验证发现问题，再交 Codex 修复                  |
| 图片、音频、模型等不可可靠合并的内容         | 保留两个版本；在最新版本上重新修改，或交用户比较选择 |
| 用户意图互相矛盾                             | 不覆盖已存在结果，询问用户需要保留什么               |

**“没有文本冲突”不代表“没有逻辑冲突”。** 例如 A 改了存档字段，B 改了另一个读取脚本，Git 可以完全不报冲突，但游戏仍会坏。

### 第五步：让 Codex 解决适配问题，不让它直接决定发布

交给 Codex 的不是一句“解决冲突”，而是一份可检索的集成材料：

- 任务原始目标与用户补充要求。
- 原始基线、最新正式版本、该任务成果及差异。
- 需要保留的其他任务目标与已有验收约定。
- 失败的检查结果和必要的运行日志。

Codex 自行查找其他上下文，提出并实现适配结果。Beaver 不通过工种列表替它拆分方案，也不因它说“已解决”就跳过检查。

反复出现同一个失败时，不能无限消耗额度或偷偷放宽标准。保留可恢复状态、失败原因和全部成果；按用户设置的停止条件处理，无法判断产品取舍时进入“需要你决定”。这不是把冲突强行标为完成。

### 第六步：验证的是最新组合结果

检查应按改动风险分层：

- 文档、配置与本地化：格式、引用、键值与基础约定。
- 脚本、场景与资源：Godot 导入、语法、加载、相关测试与场景运行。
- 功能组合：例如新增自动存档后，原来的手动存档与继续游戏仍然可用。
- 高风险变更：扩大测试范围；需要时由另一个只读 AI 审查差异。
- 视觉与玩法质量：由用户看素材、试玩并认可，不能用“编译通过”替代。

具体依赖和上下文仍由 Codex 判断，应用只要求约定的最低检查必须有真实结果。第二个 AI 的 review 是补充，不是正确性证明；缺少测试时，检查覆盖不足必须明确记录。

### 第七步：再次确认版本，受控发布

候选项目测试通过后，先确认正式项目仍是它验证时的那个版本。期间如果另一个任务或人工编辑改变了项目，就不能拿过期测试结果直接发布，必须更新候选版本并重新检查。

实施上可以在项目写入锁内检查预期 revision 与文件摘要，再写入。耗时的 AI 修复与测试不占用文件写入锁；集成排队与调度负责避免任务长期互相使验证过期。

正式写入应有持久化操作日志、写入前后摘要和幂等恢复标识。文件系统中的多文件写入不是天然的数据库事务：崩溃时依靠日志恢复或撤销已确认的写入，不能声称每个外部程序永远看不到中间状态。Beaver 自己的试玩、导出和内容浏览应读取稳定版本，或等待发布完成。

## 3. 文档与素材也必须遵守这一套规则

### 人工修改文档

资料页打开文件时记录其版本。用户保存时，如果文件已经被 AI 或另一处人工编辑更新，保留当前草稿，并比较旧版、当前版和草稿；不能无条件覆盖。

人工保存同样经过受控写入入口，并记录为一次轻量修改，而不是要求用户为了改一个字先创建复杂任务。用户还没保存的编辑缓冲区也不能被后台刷新替换掉。

### 二进制素材

不能把两张 PNG 或两份 `.blend` 当成普通文本直接合并。Git 对没有明确合并语义的二进制文件也采用保留冲突、等待处理的方式。[Git 文件合并属性说明](https://git-scm.com/docs/gitattributes)

建议素材使用稳定标识与不可变内容版本。A、B 各自生成变体，不争抢同一个输出文件；再受控决定哪个版本是游戏当前使用的版本。必要时 Codex 在最新模型上重新实施另一任务的修改，而不是拼接两份二进制文件。

素材版本和引用它的场景、脚本、文档需要作为同一份候选改动验证。只保住两个文件，却把场景引用弄坏，仍然不算解决。

### 最小归档标准

可以先定为“按内容分目录、一份文档描述一个相对独立的对象、每项有稳定标识和版本”。类型、名称、标签、关联对象用于检索，文件内容仍是事实来源。

避免把所有人物写进一个巨型文档，或让所有任务争改一个中央索引文件。搜索索引由归档结果派生，并标记对应的项目版本；旧索引不能伪装成最新事实。已有项目可以通过映射接管，不为符合目录模板而先强行搬迁全部文件。

文件标识解决“它是谁”，版本解决“我改的是哪一份”；目录分类解决“我去哪里找”。三者不能互相替代。

## 4. 回退不能把后来的任务一起抹掉

这是并行任务最容易漏掉的部分。

假设 A 开始于 V10，但它真正合入前，正式项目已经到 V12。那么 A 的回退依据应当是 **它实际发布的 V12 → V13 变更**，而不是拿启动时的 V10 整项目覆盖回来。

- **标准回退**：对当前项目执行可确定的反向变更，保留无关任务结果；后续改动使反向操作不再安全时，拒绝覆盖。
- **对话回退**：另起一个适配任务，让 Codex 根据原任务前后版本与当前项目移除相应效果，之后仍走验证和发布流程。
- **保留部分文件**：必须检查引用关系，不是勾选保留一个脚本就假定一定可运行。

如果 B 依赖 A 创建的接口，就不一定存在“完整移除 A，同时让 B 原封不动继续工作”的答案。此时需要保留兼容接口、适配 B，或由用户决定连带回退；不能承诺数学上不可能的独立撤销。

## 5. 还有一个不能省略的前提：真正限制写入范围

**独立工作目录不是安全沙箱。** Codex 如果仍能通过绝对路径修改正式项目，或者连接到指向正式工程的同一个 Blender / Godot 实例，前面的流程就可能被绕过。

因此正式方案需要保证：

1. 任务只能写自己的工作区及明确授权的输出位置；只给上下文提示词不够，必须有实际权限或执行隔离。
2. Godot、Blender、MCP 连接与临时目录能明确归属到任务。不能因都叫“Blender MCP”就共享同一个可写场景；暂时无法隔离的资源需要排队独占。
3. 素材副本不能使用会共享可写内容的普通硬链接来冒充隔离。可以考虑有写时复制保证的方式，或真实副本。
4. 文件外的副作用另行管理：安装插件、修改全局配置、部署服务器和外部付费请求，不能靠项目回退撤销。

跨平台实现形式需要单独验证。如果某种工具链暂时无法受控隔离，就对它降级为排队执行，而不是继续声称所有任务都具备安全并发。

用户从外部编辑器直接写入已接管目录，也是需要明确的边界。检测文件变化和写前检查可以减少风险，但无法替代操作系统权限，不能保证消除检查到写入之间的竞争窗口。要提供严格保证，需要正式内容只有受控写入者；开放外部任意写入时，应标明保护限制，并在检测到干扰后暂停发布、保留双方内容。

## 6. 用户界面应该有多简单

默认只需要这些状态：

**执行中 → 正在整合 → 待验收**；不能自行判断时显示 **需要你决定**。

任务尚未合入正式项目的文档或素材，只在任务结果或明确的预览状态中展示，不能静默替换资料页与素材库里的正式内容。

正常冲突不打断用户，后台自行适配。确需用户决定时，用目标或效果描述问题，例如：

> 一个任务移除了存档，另一个任务需要读取存档。这个游戏还需要存档功能吗？

提供“补充要求”“比较结果”“稍后处理”。不要默认把 Git 冲突标记、分支树或内部工作流变成普通用户的必修内容。

## 建议确认的原则

**并行创作，串行发布；可自动适配的自动处理，无法确定的保留双方；任何任务都不能靠覆盖其他任务的成果来宣称自己完成。**

方案的验收也应围绕这些底线：同文件不同段、同段、跨文件依赖、删除与重命名、二进制双版本、人工保存竞争、测试后版本变更、发布中崩溃，以及回退后仍保留后来任务。文件不丢只是第一层，组合后的游戏能运行、目标未被悄悄丢弃，才是完整结果。
