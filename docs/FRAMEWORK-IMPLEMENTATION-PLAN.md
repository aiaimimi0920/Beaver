## 1. 本轮目标与范围

完成后，用户可以从“创作”提交目标，由 Codex 补全需求或追问，并提出对象和任务拆分；Beaver 保存、调度和执行这份计划。用户也可以从“对象”直接排入一次修改，从“制造”介入具体步骤。三种入口操作同一套对象、任务和执行记录。

每个对象拥有自己的版本、组件、引用和串行修改队列。每次制造保存真实输入、提示词、工具调用、尝试、验收证据和输出。通过验收后发布新版本，下一项修改才获得写入权。主对象展示 Godot 中的实际效果，三维子内容展示 Blender 中的制作内容，标注能携带可追溯的位置上下文。

本轮包括项目 `.beaver` 存储及迁移、三种对象导入、粗中精任务、对象队列、制造编排、插件及检查工具接入、验收与发布、真实预览反馈和各入口的一致性。测试页复用已有功能，增加对象和制造来源关联。

本轮不制作具体 NPR 小阶段 Skill、人物质量规格、商业建模流水线或专用插件调用链，不要求交付一个达到美术标准的人物。不会重新设计已确认的 UI，也不扩展工作流市场、远程多租户或完整手工三维编辑器。

## 3. 实施中必须保持的规则

### 3.1 三个页面与一个任务系统

- “创作”提供粗修入口，任务泳道展示所有粒度的活动任务，并可查排队、等待、失败和历史。父子关系表示责任，依赖关系另行保存。
- “对象”展示全部语义对象，包括没有任务的对象。右侧迭代栈中的每项修改建议对应一个中修任务；空白入口绑定当前选中且没有进行中任务的对象。
- “制造”围绕选定中修任务的制作轮次展示阶段、精修任务、输入、输出和验收。阶段不必逐一等同于任务，底层每次工具调用也不新增泳道任务。
- 用户可在任意层级增补需求。独立中修无需虚构粗修父任务；精修必须属于一个中修任务和制作轮次。所有入口共享身份、权限和状态投影。
- 粗修不能只因子任务全部退出就完成；必须满足必要子任务和整体组合验收。取消必要任务需要明确调整范围并重新确认。

### 3.2 对象修改、版本及锁定

一个对象同时只允许一个中修任务拥有写入权，其精修尝试串行操作同一工作区。暂停、追问、等待验收、失败待恢复均保留逻辑写入权；只有已接受发布或完成取消处置后才交给下一项。独立对象可并行，实际共享的引擎和文件资源仍需单独调度。

自有组件共享对象的版本和修改权；引用的独立对象绑定固定接受版本，新版本只提示可更新。共享游戏场景、配置和代码路径也必须有明确所属对象，通过相应集成任务修改，不能借不同对象 ID 并行改同一文件。历史版本、引用和反馈使用的内容默认保留，本轮不自动物理清理。

工作基准分成三项保存：`basePolicy`、用户指定的版本和实际领取时固定的 `resolvedBaseVersionId`。默认策略为 `latestAccepted`，排队时不复制内容，获得修改权时解析为最新已接受版本；用户也可以明确选择 `pinnedVersion`。新建对象允许明确的空基准。

“对象”页切换展示版本只改变查看状态。“制造”页选择工作基准影响后续执行：未启动任务可修改配置；已有尝试的输入保持不可变，改基准必须暂停并通过显式重建或返工命令创建新尝试、检查点及失效记录。不会因下拉菜单变化就后台替换正在执行的文件。

从历史基准制作仍进入同一对象队列，不产生并行写分支。保留领取时的当前已接受版本作为发布比较点；如候选会替换较新的内容，最终确认需展示这个差异，不能默默合并图片或二进制文件。发布时发生新的版本漂移须返回冲突并保留成果。

迭代栈的锁图标表示需求编辑状态，与对象写入权分开。提交后保存并锁定；未启动任务解锁后按 revision 更新。运行中的修改先保存草稿，经暂停和重新规划后才影响新尝试；历史完成任务允许基于旧要求创建新修改，不回写旧结果。

插入和拖动使用持久任务 ID、相邻锚点及队列 revision。只调整未开始项，服务端复核依赖和循环；不能把运行中或已完成项拖成一个新的可执行顺序。UI 保留虚影提示，对不可移动项显示明确原因。

### 3.3 执行权与证据

Beaver 管身份、计划 revision、队列、阶段门槛、文件归属、状态、取消恢复和版本发布；Codex 管需求理解、合理假设、追问、拆分建议、工具选择和执行报告。Skill 提供步骤方法，插件与工具完成实际操作，最终状态由 Beaver 校验后写入。

模型回调核验 project / task / object / run / attempt / thread / turn 及写入代次。模型不能批准自己的人工门槛、修改 owner 策略或直接把一个对象标记为已接受。中修协调器等待精修时释放 Codex 运行槽位，保留对象修改权。

程序检查报告、AI 评价、人工决定分别保存。检查绑定冻结的输入、输出清单、工具版本和配置摘要；AI 声称通过不能替代检查报告。技术检查失败不能靠人工批准绕过。普通步骤可按既定策略自动推进，关键阶段和最终对象发布保留人工门槛。

## 4. 数据与模块边界

### 4.1 项目存储

```text
PROJECT/
  project.godot
  .beaver/
    project.json        项目 ID、schemaVersion、存储版本
    project.sqlite      项目任务、对象、轮次、队列和索引
    content/            不可变版本内容及清单
    workspaces/         对象制作工作区与检查点
    previews/           可重建帧缓存及预览索引
    evidence/           验收证据、冻结标注和报告
    operations/         文件提交、导入与恢复日志
    cache/              可重建缓存
```

目录名称在 F0 固定后作为后续契约。冻结标注和验收截图属于持久证据，不能随缩略图缓存清理。源文件、输出资源和验收文件可有不同用途，按清单关联，不能将三视图当作模型资源发布。

任务 Codex HOME 保存在 `workspaces/.codex/<task>`，任务工作副本位于 `workspaces/<task>`，恢复副本时不能覆盖会话。`.codex` 为保留分组名；其中的会话属于持久项目数据，宿主生成的配置在启动准备时重新绑定，凭据不写入项目。

全局数据只保存宿主偏好、凭据、工具安装配置、项目位置登记及可重建索引。项目相关会话和操作记录纳入迁移清单；凭据不复制进项目。项目内部使用相对路径，宿主登记负责当前绝对位置。打开项目首先识别存储版本，不能让旧 Store 自动建表改写外部来源。

### 4.2 主要身份

| 身份                               | 负责的事实                                                |
| ---------------------------------- | --------------------------------------------------------- |
| Task / PlanRevision                | 粗中精层级、父子及依赖、需求草稿与提交 revision、任务状态 |
| ObjectRecord / Component           | 语义对象、类型、名称、标签、自有组件及文件归属            |
| ObjectReference / ObjectVersion    | 独立对象的固定接受版本引用、不可变内容清单和来源          |
| QueueEntry / WriterClaim           | 中修顺序、阻塞原因、独占拥有者、领取回执及写入代次        |
| ProductionRun / Stage              | 本次制作基准、共享工作区、线性阶段及门槛                  |
| Attempt / Candidate                | 冻结输入、实际执行、检查点、输出候选和失败历史            |
| CheckReport / Judgment / Decision  | 确定性结果、AI 或 owner 评价、推进和接受决定              |
| PreviewSession / Feedback          | 引擎会话、帧及相机来源、编号标注、需求处置和影响范围      |
| ImportOperation / PublishOperation | 幂等请求、准备内容、文件日志、提交及恢复状态              |

沿用适用的现有结构，不按这张表机械建立同名空模块。现有 `AssetPick.objectId` 是引擎场景内身份，不能作为业务对象 ID。任务、阶段、尝试、候选和版本不得互相借用 ID。

### 4.3 API 与 UI 接入方式

`native/core` 负责规则和事务；`native/desktop` 负责传输、调用者身份和能力目录；`src/shared` 保存强类型契约；React hooks 保存交互草稿及查询结果，不充当调度器。外部引擎的耗时 I/O 在数据库锁外执行，提交结果时再次核验身份和 revision。

下列是需要覆盖的能力分组，新增名称属于拟定接口，F0 核对目录后再定名。已有 `task.*`、`assetTask.*`、`task.framework`、`validation.*` 应复用或显式演进，禁止不加校验地转发到两套实现。

| 界面行为                             | 需要的核心能力及接入时机                                  |
| ------------------------------------ | --------------------------------------------------------- |
| 对象列表、分类、标签、搜索、子内容   | 对象与版本查询、缩略图引用、订阅；F2                      |
| 粗修拆分、手工增补、生成对象         | 计划提案及确认、对象与任务原子关联；F3，执行在 F4-F5 开放 |
| 迭代插入、编辑、锁定、重排           | 草稿/提交 revision、队列命令及服务端资格判断；F3-F4       |
| 制造任务列表、工作基准、阶段和轮次   | run / stage / attempt 查询及受约束命令；F4-F5             |
| 保存提示词、重新生成、仅重验收       | 定义 revision、检查点、新尝试、重验收及下游失效；F5-F6    |
| 工具检查、验收图、输出资源、测试跳转 | 注册检查器、证据清单及 `validation.*` 来源关联；F6        |
| 接受、发布、取消、三种导入提交       | 冻结候选、可恢复文件操作、最终事务；F7                    |
| 预览、相机、点选、框选及编号反馈     | 实际帧、engine pick、冻结上下文、反馈处置；F8             |

写命令使用稳定 `requestId`、目标身份和适用的 `expectedRevision`。网络重试复用原请求 ID；只有新的用户操作生成新 ID。订阅带项目和实体 revision，重新连接后读取权威快照；旧项目、旧选择或旧轮次的晚到结果不能覆盖当前页面。

## 6. 验证、交付与开发纪律

### 6.1 按变更选择验证

开发什么就验证相关部分。纯文档只检查格式、链接及项目要求的结构门禁；业务规则使用对应核心/契约用例；真实引擎、安装或渲染边界使用定向运行检查。历史通过记录不能充当新增能力的证据，也不因累计改动多就默认运行全套。

现有命令可按实际改动选用，不是每批必跑列表：

```powershell
# 只在对应 TS/React 契约变化时使用
rtk proxy npm run typecheck
rtk proxy npx tsx --test tests/task-plan.test.ts tests/asset-work-panel.test.ts

# 框架操作或验收模块发生变化时选择相关目标
rtk proxy cargo test --locked -p beaver-core --test framework_operations --test framework_validation
rtk proxy cargo test --locked -p beaver-core --test framework_evidence
rtk proxy cargo test --locked -p beaver-core --test task_callback --test asset_work_recovery
rtk proxy cargo test --locked -p beaver-desktop business_mcp::tests::callback_mcp_stream_http_core_roundtrip

# Rust 改动至少包含一次相匹配的编译验证
rtk proxy npm run check:native
rtk proxy npm run check:effective-lines
```

新领域测试在所属批次按真实失败边界新增，不照搬实现条件凑覆盖率。测试命令记录实际目标，不能把尚未创建的测试文件写成已经执行。修改文件运行仓库工具链的定向格式化，避免重排无关文件；不默认调用包含全量测试与 Electron 构建的 `npm run check`。

Rust 和原生构建从相同 PowerShell/MSVC 环境运行，保留 `LIB`，日志写入 `output/` 后再提取结果。遵守 [代码结构规则](../resources/instructions/code-structure.md) 和 [模块边界](CODE-STRUCTURE.md)，不提高 baseline 接受新超限文件。

### 6.2 原生交付
