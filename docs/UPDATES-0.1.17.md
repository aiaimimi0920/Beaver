# Beaver 0.1.17 - 本地试玩与玩家程序交付

## 本轮完成

本轮继续落实实际应用，重点完成游戏页到可运行成品的入口及完整性检查，并使用真实 Godot 重新验证起步游戏。当前仍不能宣称最初约定的整个产品已经全部开发完成；剩余必需项见文末。

### 游戏页可直接试玩和导出

检查现有界面发现：原来的试玩、导出操作挂在部分旧页面标题栏，而新的主要创作、资料、素材、游戏总览页面会隐藏该标题栏。

现在在「游戏」页面左侧增加两个直接入口：

- **试玩游戏**：使用已配置/检测到的 Godot 启动当前项目。
- **导出游戏**：打开真实导出对话框，选择预设和项目外输出目录，生成玩家程序。

保留左上方游戏名字和右侧设定卡，不重新塞入大量标题及说明。

同时修复游戏总览把自身最小高度设为整页高度、再叠加上方页签而产生的多余纵向滚动。最终 r2 包通过游戏页实际溢出检查，不是简单隐藏滚动条。

### 不再只检查一个 EXE

新导出的 `export-manifest.json` 升级为 v2：

- 记录整个交付目录中的程序、资源包、动态库等文件的相对路径、字节数和 SHA-256。
- 导出结束自动复核文件数量、每个文件的大小与摘要，以及目标平台入口的基本文件头。
- 「校验已有导出」可选择一个已有交付目录并再次检查，不会执行其中的程序。
- 缺失资源包、额外文件、被修改的文件、重复清单路径、越界路径、符号链接和错误平台文件头会拒绝通过。
- 诊断日志与清单自身不作为玩家负载参与校验。
- 旧清单只记录入口摘要，明确要求重新导出，不把它当作完整资源验证。

完整性校验不等于数字签名、可信发行者验证、运行验证或玩法验收。

### 导出保护

- 导出前检查项目是否有未完成的恢复日志，避免交付恢复到一半的内容。
- 用真实路径的相对关系检查导出目录，禁止输出到项目自身或其子目录。
- 每次使用独立临时命名目录，避免同时导出时按毫秒命名碰撞。
- 使用流式摘要，不再为了验证大型入口程序把整个文件一次性读入内存。

### 环境问题与边界

初次无显式配置时选中了 PATH 中的 Godot 4.0.2，导入验证未通过；另一个目录虽叫 `godot-4-4-1`，实际程序却是 4.5.2 RC 自定义构建，且个人目录缺少匹配导出模板。最终显式选用已存在并实测可用的 4.6 构建，以及 Beaver 验证目录中的模板，通过仅本次测试的 APPDATA 环境使用，没有覆盖个人 Godot 配置。

不能根据文件夹名称推断引擎版本，也不能把一次指定环境通过当作干净机器自动安装已经完成。官方模板目录版本约定见 [Godot 构建文档](https://docs.godotengine.org/en/stable/engine_details/development/compiling/introduction_to_the_buildsystem.html)。本次使用已安装模板，没有重新下载或重新校验来源归档；验证脚本已删除误导性的固定归档摘要。
