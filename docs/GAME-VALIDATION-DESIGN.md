## 1. 我们的想法与已确认的产品规则

我们希望 Beaver 在制作游戏时，既能自动检查代码，也能把游戏当前的画面和玩法过程展示给用户。用户通过截图或视频指出需要修改的地方，再由 AI 继续完成修改，尽量减少必须亲自进入游戏才能反馈的情况。

讨论中最重要的调整是：普通大任务的完成与画面查看分别推进。代码验收通过后，应尽量自动完成大任务；画面采集、AI 画面判断和用户查看可以继续在后台进行，不能让每个任务都等待用户逐张确认。

已确认规则如下：

1. 代码验收以 Godot 的 GUT 插件为基础。失败项标红，AI 尽量自动修复，用户也能通过聊天指定修复方向。
2. 画面按漫游、功能、UI、任务四类组织；产物支持静态截图和一段时间的视频。
3. 每组画面背后保存可再次执行的流程。重新点击后，在当前游戏版本上产出大致相似的玩法过程；代码修改导致画面变化是预期行为。
4. 画面要保留相关代码、场景、资源和任务的关键指引，供后续修改作为上下文。视频需要按时间片段定位。
5. AI 和人都能查看、判断画面。用户认为有问题时，可通过对话创建修改任务或子任务。
6. 本功能位于 Beaver 内部、按游戏项目组织的独立 Tab 中。建议页面名为“测试与画面”。
7. 提供开关“正式发布前强制运行一次画面诊断”，默认开启。
8. 开关开启时，正式发布前重跑所有相关流程，生成新画面，与用户最后一次明确认可的对应画面对比。疑似异常标红；用户确认正确后可转绿。代码和画面全部为绿才允许正式导出发布。
9. 开关关闭时，取消强制画面重跑及画面绿灯限制；正式发布仍要求代码验收通过。
10. 当前 Beaver 开发、调试和内部验证阶段暂不执行上述“全部为绿才能发布”的新限制。不能据此要求当前 Beaver 开发先达到全部测试通过。

本页与[资产制作任务窗口开发设计](ASSET-TASK-WINDOW-DESIGN.md)分别实施。资产制作仍采用此前确认的独立窗口；本设计中的独立 Tab 专门承载游戏代码验收、画面流程、反馈和发布诊断。

## 2. 三条独立推进的流程

### 2.1 日常任务完成

目标流程为：AI 开发 -> 代码验收 -> 必要的自动修复 -> 验收通过并完成安全合入 -> 自动完成任务 -> 后台生成或更新相关画面。

代码失败可以阻止该任务交付。画面尚未生成、画面疑似异常、用户尚未查看，都不把已完成的普通任务改回未完成状态。用户后续提出修改时，创建关联的新工作，保留原交付及其证据。

自动完成仍受既有任务依赖、文件冲突、未回答问题和恢复状态约束。代码通过不能覆盖他人修改、跳过合入冲突，或把未完成的子任务视为完成。

`completed` 与 `accepted` 继续分开记录。新任务默认自动审批；有运行内容改动的任务先通过集成候选的 GUT，父任务在全部子任务已完成并审批后再检查集成结果。通过检查并安全合入后自动完成审批，不新增画面人工确认关卡。用户主动选择的手动审批策略及旧任务的既有策略继续保留。

### 2.2 日常画面展示与反馈

目标流程为：选择或生成流程 -> 固定本次游戏版本 -> 运行游戏 -> 截图或录像 -> 展示结果 -> AI 或人提出意见 -> 关联修改任务 -> 重新运行对比。

日常画面中的红色表示“需要关注”，用户可以暂不处理并继续开发。页面要能同时展示“任务已完成”和“画面待生成/需要关注”，避免用一个总状态掩盖两者差别。

### 2.3 正式游戏发布

| 使用场景                         | 代码要求                               | 画面要求                       | 对结果的处理                         |
| -------------------------------- | -------------------------------------- | ------------------------------ | ------------------------------------ |
| 普通大任务交付                   | 对应范围代码验收通过，满足既有合入规则 | 异步生成和查看                 | 画面不阻塞普通任务完成               |
| 正式发布，开关开启               | 发布候选的全部必需代码测试通过         | 当前发布诊断的全部必需项目为绿 | 任一未完成、失效或红项均不能正式发布 |
| 正式发布，开关关闭               | 发布候选的全部必需代码测试通过         | 不要求强制运行或全绿           | 画面红项保留，但不阻塞发布           |
| 当前 Beaver 开发、调试、内部验证 | 如实运行并记录本轮应做的检查           | 按验证目标运行                 | 暂不启用本设计新增的正式发布限制     |

人工确认画面只改变画面判断，不能把失败的 GUT 结果改成通过。

## 3. 独立 Tab 的页面与操作

“测试与画面”使用 Beaver 现有项目切换和导航体系，持久化数据按 `projectId` 隔离。从任务详情打开时，直接定位到该任务关联的流程和结果。

建议页面分为三个区域：

- 顶部：当前项目、被查看的游戏版本、代码测试概况、画面流程进度、发布诊断状态，以及完整开关名称。
- 左侧：代码结果和四类画面流程的列表，可按任务、状态、最近运行筛选；每项显示执行状态、画面判断、最新运行时间和版本。
- 主区域：截图/视频播放器、关键帧或采集点、历史运行切换、当前结果与认可基准对照；右侧提供关联代码和对话反馈。

列表操作包括“运行流程”“重跑全部”“停止本次运行”“查看历史”；画面操作包括“标记正确”“提出修改”“与认可画面对比”。发布入口调用专门的发布诊断流程，不把普通“重跑全部”直接当作正式发布凭据。

对话默认携带当前选中的流程、证据和版本。对视频还带入播放时间或所选时间段；对截图允许带入所选画面区域。用户也可以直接文字描述，区域标注属于建议增强项，不作为本轮额外确认的硬性需求。

所有状态同时显示文字和颜色。准备环境、导入、运行、采集、编码、对比均显示实际阶段；执行时保留历史画面可查看，不以冻结界面表示忙碌。进度由已完成步骤或采集点计算，无法估算的操作显示忙碌状态。

## 4. 代码验收与修复闭环

### 4.1 GUT 接入范围

首个实现固定 GUT 9.4.0，面向 Godot 4.4 及之后的 4.x。插件以校验摘要的归档随 Beaver 分发，仅解压到隔离运行副本；已接入结构化报告、超时取消和本次进程清理。具体来源和分发方式见[运行依赖说明](../resources/validation/README.md)，不修改个人 Codex 工具链。

Beaver 保存每次测试所用的游戏快照、GUT/引擎版本、用例清单、通过/失败/跳过数量、耗时、日志和失败定位。退出码、报告完整性、实际执行用例及引擎错误需要联合检查；只看到进程正常退出不足以标绿。

任务级验收覆盖相关行为和必要回归；父任务结束时应对集成结果运行对应检查。正式发布执行项目登记的全部必需代码套件。报告必须显示覆盖范围，避免把“本次用例通过”解释成所有代码质量已有保证。

AI 根据任务的可测试验收条件补充 GUT 用例，并把测试文件和运行清单作为任务成果管理。新项目缺少测试配置时，先由相关开发任务建立最小可运行套件；用户不必手动编写测试才能使用此功能。用例应检查有意义的行为和边界，避免只照搬实现或用无条件成功充数。

插件缺失、报告缺失、执行中断和应运行用例被跳过，需要显示具体原因。没有测试的项目显示“尚未建立代码验收”，不能自动得到发布绿灯。纯资料等无代码变更任务可以注明“不新增代码测试”，沿用其适用的既有规则；这不免除正式发布的项目级代码检查。

### 4.2 修复过程

1. 将失败用例、断言差异、调用栈、相关文件和被测版本交给 AI。
2. AI 在受控任务工作副本中定位和修改，保存修复任务与失败运行的关联。
3. 对新版本重新运行失败用例及受影响检查。新的通过结果替代当前状态，历史失败记录继续保留。
4. 若修复扩展到其他模块，更新受影响测试范围；不通过删除断言、排除失败用例来消除红色。
5. 用户可在同一上下文中补充修改方向；影响已经交付内容时创建关联后续任务，不覆盖原任务历史。

每轮自动修复继续受任务时间限制，首版自动尝试上限为 2 次。相同失败指纹再次出现或缺少可用引擎时停止自动重试；保留原因和失败运行，允许用户继续指导。次数上限属于当前实现策略，不改变原先“尽量自动修复、必要时由人指导”的产品目标。

代码测试应运行在将要交付的候选内容上。并发合入改变候选内容时，需要重新形成候选并检查；不能拿旧工作副本的绿灯证明新的集成版本。耗时测试放在后台，最终合入前重新校验版本，避免长期持有项目或数据库锁。

## 5. 可重新执行的画面流程

### 5.1 四类流程

| 分类 | 内容                                                     | 重播依据                                                                 |
| ---- | -------------------------------------------------------- | ------------------------------------------------------------------------ |
| 漫游 | 在约定区域随机移动、交互，按配置定期或随机采集           | 保存随机种子、实际动作和路线；重播默认沿用已有轨迹，探索新轨迹创建新记录 |
| 功能 | 围绕某个功能或玩法执行明确过程，如攻击、制作、背包或对话 | 起始状态、动作、事件等待及前后关键采集点                                 |
| UI   | 呈现菜单、弹窗、列表、不同数据量和状态下的界面           | 固定分辨率、语言、输入方式和触发条件；保存各状态的采集点                 |
| 任务 | 展示某次大任务的直接成果及必要关联过程                   | 关联任务与上述流程；可聚合多个流程，也可有独立任务流程                   |

类别用于组织和检索，同一流程可以被多个任务引用。发布时按流程版本和运行配置去重执行，任务分组仍保留各自引用和结果，不重复运行同一底层流程。

### 5.2 流程的最小定义

每个流程保存稳定的 `flowId` 和随编辑递增的 `flowRevision`，包含：

- 目的、所属分类、关联任务，以及应当呈现的玩法结果。
- 入口场景、初始存档或准备步骤、运行配置、随机种子和所需资源。
- 动作序列，如点击、移动、按键、交互；尽量使用稳定节点或游戏语义定位。
- 等待条件，例如场景进入、状态值变化、动画结束或 UI 可见，并为等待设置超时。
- 稳定的步骤与采集点标识；截图时机、区间采集规则、视频起止点及期望证据数量。
- 相关场景/代码指引、允许变化区域、重要观察点和清理要求。

优先按游戏状态等待，必要时采用有上限的时间等待。不能单靠固定延迟假定加载或玩法已经完成。

AI 可根据开发目标和改动生成或更新流程。大任务完成后先登记关联的画面待办，再异步准备和运行；暂时无法建立流程时显示“缺少可运行流程”及原因，不阻塞已完成任务。正式发布诊断需要把这些缺失纳入覆盖检查，不能因未登记成功而漏掉任务画面。

### 5.3 可比性的边界

重播要求玩法内容与关键阶段可比较，不要求逐像素一致。游戏版本、流程版本、分辨率、语言、图形设置、初始存档、随机种子、运行器版本均进入运行记录。

漫游同时支持“重播这条路线”和“重新随机探索”。新探索生成新轨迹；用于发布比较时重播对应认可基准的轨迹，避免用不同探索内容直接计算匹配度。

存档准备和运行使用本次隔离的用户数据目录，不能污染用户正常试玩存档。测试桥可以加载约定初始状态和发送输入，不能绕过待展示的真实玩法逻辑来生成看似成功的画面。

代码变化导致旧动作、节点或状态条件失效时，报告流程失效。AI 可以提出流程修订；修订保留版本和原因，不能悄悄跳过失败步骤、改用无关场景截图，再把旧流程标成成功。

### 5.4 截图与视频

静态证据必须来自本次实际运行的游戏画面，并记录采集点和状态。视频必须来自本次真实过程，记录时间轴、关键事件、动作和关键帧；不能把若干静态图轮播包装成完整玩法录像。

建议首个实现适配器由受控 Godot 运行会话提供状态、输入及渲染帧，随后接入视频编码。GUT 的无界面运行与画面流程的有渲染运行分别管理。若采用已有窗口截图能力，必须绑定本次游戏进程/窗口并验证画面有效；不能依赖任意当前前台窗口。

后续需用一个真实流程验证运行适配器、后台渲染、输入和录像方案。可以评估现有 Godot 自动化工具，但不预设个人安装的 PlayGodot 或专用引擎已经随 Beaver 分发。

窗口不可采集、录像截断、关键帧缺失或采集点数量不足均显示运行异常。保存已经获得的部分证据及日志，同时明确本次流程未完整完成。实际游戏呈现的黑屏先作为疑似画面问题展示，允许结合预期过渡场景判断；采集失败产生的空结果需单独标识。

## 6. 证据、代码指引与对话上下文

每次运行生成独立的 `runId`；每张截图或每段视频有独立 `evidenceId`。新的运行不覆盖旧文件，流程重跑也不改变历史证据对应的代码版本。

代码指引至少包括游戏快照、项目相对路径、场景/节点和相关脚本。能够定位时补充函数/符号、资源引用、采集时状态和相关日志。行号作为辅助信息，不能成为唯一定位方式；代码变化后仍可打开当时的文件或查看与当前文件的差异。

自动关联来源要明确：运行时明确报告、流程作者指定、AI 推断分别标记。无法准确定位时保留场景和候选脚本，不编造精确行号。视觉问题也可能来自材质、纹理、主题和布局资源，需要一并保存引用。

视频按时间段记录上下文，例如“00:12-00:18 打开背包：对应背包场景、UI 脚本和动作步骤”。用户选中该区间发出“打开时按钮被遮住了”，新任务可直接获得那一段证据和相关代码。

建议反馈形成结构化记录：用户原话、流程/运行/证据标识、截图区域或视频区间、当时版本、关联代码，以及生成的任务标识。已有未结束任务可沿用其对话入口；已交付任务使用关联后续任务，独立问题可创建新任务或子任务。

修复完成后，自动建议或安排重跑原流程。原始意见、修复任务、修复前后证据形成可追踪关系；只有实际得到新证据后，才显示“已验证修改效果”。代码通过和用户满意分别记录。

## 7. 认可基准与画面判断

“用户最后一次认为正确的画面”具体定义为：对应流程和兼容运行配置下，用户最近一次显式确认正确的完整运行证据。基准按认可时间选择，不能使用最近生成、最近浏览或 AI 最近通过的画面替代。

建议一个基准包含流程的整组必需采集点及视频片段，同时允许逐项查看和确认；未全部确认时保留剩余待确认项。只确认一张截图，不会替其他未查看的必需片段建立认可记录。

用户确认一组新画面正确后，将其设为该流程的新认可基准，并保留上一基准与确认记录。AI 的自动通过只改变本次判断，不自动推进用户基准。若用户从历史中认可旧运行，须明确它的版本，不能顺便批准另一个发布候选。

基准兼容性由流程采集点、运行配置和场景语义决定；比较不同游戏代码版本是正常用途。流程语义改变、采集点无法对应或配置不同，需明确提示“需要新基准/不可直接比较”。

日常查看允许只展示证据、不运行 AI 对比。正式发布且开关开启时，必须完整取得新证据并完成对应判断。

## 8. 正式发布前的画面诊断

### 8.1 开关开启

开关“正式发布前强制运行一次画面诊断”按项目持久化，默认开启；发布页面展示本次实际采用的值。

1. 建立发布候选，固定游戏代码/资源快照、导出目标、流程清单与版本、运行配置和诊断策略。
2. 对该候选运行全部必需代码测试。
3. 重跑项目所有适用的已登记画面流程，覆盖漫游、功能、UI、任务；缺失流程和未完成覆盖也形成可见条目。历史运行本身不重复执行，引用相同底层流程的任务可共用本次结果。
4. 生成属于本次发布诊断的新截图/视频，与各流程最后的兼容用户认可基准逐项对比。历史绿灯不能替代本次新运行。
5. 自动判定符合的项目变绿，并注明自动判断；疑似异常标红，展示原因、关键区域或视频时间点，等待用户查看。
6. 用户确认新结果正确后，该结果变绿，并保存真实确认来源；用户要求修改时创建关联任务。修改形成新的候选，再对新候选执行检查。
7. 仅当本次候选全部必需代码测试和画面诊断项目为绿时，允许正式导出。导出使用同一份候选快照，并继续执行现有导出及产物完整性验证。

“所有适用流程”应由项目版本化清单确定，不按本次是否执行成功临时缩小。已经删除的玩法或明确退役的流程可记录原因后退出后续清单；失败流程不能自动退役。发布时显示所覆盖和所排除的范围，避免静默漏检。

每个诊断项在比较开始时保存实际使用的基准标识、判断规则和版本。后续人工认可产生新基准，不倒改已记录的比较对象；重新比较需要产生新的判断记录。

### 8.2 匹配度与人工处理

匹配度用于发现疑似变化。建议先按同一流程步骤/采集点对齐，再结合画面结构、关键区域、文字和必要的玩法状态判断；对时钟、粒子、随机背景等允许变化区域使用明确规则。

阈值和容差可按流程配置并版本化。本设计不预设一个适用于所有游戏的固定百分比，也不承诺整图高相似度可以证明玩法正常。局部重要按钮缺失、交互没有发生或错误状态仍可能需要标红。

视频对比按动作和关键事件阶段对齐，容许合理时长变化，检查必需片段及状态转换；不能仅比较首尾帧。无法可靠判断的内容标红交给用户查看，不编造自动通过结论。

以下情况需区别处理：

- 新证据完整、存在疑似差异：用户可以确认正确并转绿，也可以要求修改。
- 首次运行、没有认可基准：提示需要首次确认；用户确认完整结果后建立基准并转绿。
- 执行失败、未采集到有效证据或证据不完整：显示运行异常，先修复或重跑；空结果不能靠“确认正确”变绿。
- 结果对应其他候选、旧流程或不兼容配置：显示已失效，不能给当前候选放行。
- 代码测试失败：保持代码红色，画面人工确认对此无效。

人工确认必须绑定具体诊断项、运行、证据及候选版本。任务对话中的自动判断能力不能把 AI 决定登记成用户亲自认可。

### 8.3 开关关闭及途中变更

关闭后，正式发布跳过强制画面运行和画面全绿要求；仍需该发布候选的全部必需代码测试通过。正常画面 Tab、历史、手动重跑、对话反馈及已有基准继续可用。

关闭开关不会把画面红项改绿，也不会把未执行诊断写成成功。发布记录注明“本次未要求画面诊断”。重新开启后，下一次正式发布必须生成新的诊断结果。

建议每个发布候选固定采用的开关值。用户在检查过程中修改开关时，明确重建发布检查上下文，避免在同一份记录中混用两套规则。

### 8.4 版本与开发阶段例外

游戏修改、流程修订和诊断配置变化不能继续沿用旧候选的绿灯。可以继续发布已经检查的固定快照；若选择更新后的当前项目，需要建立新候选。正常编辑不必为了等待人查看而被长期锁住。

正式发布记录保存代码运行、画面运行、基准、自动/人工判断、开关值和最终导出快照之间的关系。现有包完整性验证继续保留；画面全绿不会自动证明导出的可执行文件已在目标平台运行成功。

当前 Beaver 开发、调试及内部验证不启用本节新增的全绿限制。2026-09-13 的实现已区分 `internal` 与 `formal` 导出用途：内部导出保留既有通路并记录用途，显式选择游戏正式发布时执行候选校验。检查失败仍如实展示。

## 10. 建议的数据、接口和模块边界

### 10.1 数据对象

以下为拟议对象，不表示数据库已有这些字段：

| 对象             | 主要内容                                                      | 更新规则                                     |
| ---------------- | ------------------------------------------------------------- | -------------------------------------------- |
| `ValidationFlow` | 项目、分类、目的、任务引用、流程版本、准备/动作/等待/采集规则 | 编辑形成新版本；稳定标识保留                 |
| `CodeTestRun`    | 快照、套件、引擎/GUT 版本、结果、失败定位、日志、修复任务     | 每次检查独立保存，不能把旧版本成功用于新版本 |
| `VisualRun`      | 流程版本、游戏快照、配置、随机轨迹、执行步骤、状态、证据清单  | 每次重跑产生独立记录；失败可保留部分证据     |
| `Evidence`       | 文件内容摘要、媒体类型、采集点或视频时段、代码/资源指引       | 原始证据不可被新运行覆盖                     |
| `VisualBaseline` | 对应流程/配置、被认可证据、用户确认时间和来源、前一基准       | 仅用户显式认可推进；保留历史                 |
| `VisualFeedback` | 用户原话、所选证据/区域/时段、版本、后续任务引用              | 与任务和重跑结果关联，不倒改原证据           |
| `ReleaseCheck`   | 候选快照、流程清单、开关/策略版本、代码及画面结果、导出记录   | 放行仅适用于其固定候选与检查范围             |

游戏版本建议由现有文件内容快照生成稳定摘要；不依赖项目必须存在 Git 提交。代码、资源及影响行为的配置均纳入版本，生成的录像、运行日志和导入缓存不反向改变游戏版本。

元数据建议沿用现有本地存储和事件机制，媒体保存到 Beaver 项目关联的数据目录，不默认混入游戏资源。基准、发布凭据和仍被反馈任务引用的证据应保留；历史清理需要展示影响范围。备份恢复要同时覆盖元数据和其媒体文件。

### 10.2 状态和共享业务接口

执行状态与判断结果分别存储。执行可以是排队、准备、运行、采集、对比、完成、失败或取消；画面判断可以是未判断、自动通过、用户通过、需要查看、缺少基准或已失效。绿灯需要可追踪的运行和判断依据。

建议新增的业务操作如下，名称仅为设计草案，开发时再与当前业务目录对齐：

- `validation.code.run`：启动代码验收，返回运行标识。
- `validation.flow.list`、`validation.flow.save`：查询、登记和版本化编辑流程。
- `validation.flow.run`、`validation.run.cancel`：运行或取消指定流程。
- `validation.run.get`：读取状态、步骤、日志摘要与证据引用。
- `validation.evidence.confirm`：确认具体运行证据，登记人工认可与基准。
- `validation.feedback.create`：保存反馈并创建或关联修改任务。
- `validation.release.start`、`validation.release.get`：创建及查询正式发布检查。

耗时调用立即返回任务/运行标识，通过事件或查询读取进度。调用需要项目、流程/证据、预期版本等明确参数；重复请求和重复确认按请求标识幂等处理。确认时校验结果版本，防止用户正在查看的结果被后来运行替换。

现有 `game.export` 的正式发布路径需要在共享后端校验发布候选和策略，UI/API/MCP 不能各自计算不同的放行结论。试玩、内部验证和正式发布的行为在接口语义上明确区分。

### 10.3 模块与并发

建议在原生核心中按代码运行器、流程执行、证据存储、基准/对比、发布判断拆分模块；桌面层负责引擎会话、输入/采集适配、取消与业务调度；UI 单独维护列表、播放器、对比与反馈组件。

拟议目录可以采用 `native/core/src/validation/` 与 `src/ui/validation/`，测试桥及流程格式单独归属。避免把逻辑集中追加到现有任务完成函数、`App.tsx` 或单个巨大运行器中。遵守[代码结构规则](../resources/instructions/code-structure.md)及[文件职责与检查要求](CODE-STRUCTURE.md)。

普通任务队列、代码验收队列和画面队列各有状态及取消语义，画面任务不能占住普通任务的完成锁。首版建议同一项目串行运行画面流程，不同运行使用独立数据和输出目录；后续并发优化需以实际渲染资源和隔离能力为依据。

运行器记录自己启动的进程和会话。取消、超时和退出仅清理本次持有的进程，不按名称终止用户正在使用的 Godot、Blender 或其他应用。重启后将未完成运行标为中断并提供重跑，保留已写入证据。

## 11. 与人物 skill 及其他开发的边界

人物建模 skill 负责制作内容；本功能负责检查游戏代码、执行游戏流程、保存证据和承接反馈。场景、对象和资源指引可由 skill 或任务报告提供，但首版不能依赖人物 skill 必须先改造完成。

初始设计阶段只新增本文和文档索引。实际开发使用独立目录和分支，UI、运行器和数据模型由同一负责人整合；人物 skill 的修改由原开发任务保留，合并时单独核对其最新内容。

画面验收发现角色、服装或资产问题时，可以创建关联资产修改任务，并跳转此前设计的资产制作窗口。两个功能共享任务和资源引用，不把游戏画面 Tab 扩展为第二套建模工具。

## 12. 后续实施顺序与完成条件

以下保留原定实施顺序。2026-09-13 已实施第 1 至 5 项的功能代码并完成核心及适配器验证；第 6 项的完整原生应用验收仍待独立测试时段。各项的实际证据和边界见实现记录，不能把代码实现等同于全部应用场景验收通过。

1. 建立最小运行闭环：固定候选快照，运行真实 GUT 用例及一个有渲染的画面流程，验证初始状态、输入、截图和清理；固定工具版本与流程格式。
2. 完成代码验收集成：结果落库、失败标红、自动修复上下文、用户指导、默认自动任务验收；验证并发合入和父子任务规则。
3. 完成 Tab 和四类流程：登记/编辑/重跑、状态、截图历史、任务聚合、代码指引与反馈任务。任务完成后异步生成画面。
4. 完成视频和认可基准：录像、事件时间轴、视频上下文、人工认可历史，以及与新运行的对比。
5. 完成发布诊断：全量新运行、匹配判断、人工转绿、版本绑定、开关开启/关闭，以及当前开发阶段例外。启用正式限制前单独记录启用范围和日期。
6. 完成真实应用验证：通过 Beaver 的公开业务入口完成闭环，补齐中断恢复、缺失证据、过期结果、备份恢复和跨页面定位验证。

行为验收至少覆盖：

| 场景                           | 必须观察到的结果                                          |
| ------------------------------ | --------------------------------------------------------- |
| 代码通过，画面仍在排队         | 大任务正常自动完成；Tab 显示画面待生成                    |
| GUT 断言失败，随后修复         | 红色失败可定位；修复后在新版本真实重跑，历史失败可查看    |
| 代码通过但合入冲突             | 保持冲突和恢复规则，不自动覆盖用户内容                    |
| 漫游流程重复点击               | 使用相同起始条件与轨迹呈现可比较过程，分别保留运行记录    |
| 代码修复后重跑功能/UI 流程     | 使用当前代码；能查看旧、新画面及各自代码上下文            |
| 用户针对视频区间反馈           | 修改任务收到正确时间段、流程动作、游戏版本和代码/资源指引 |
| 画面失败或代码通过后用户不满意 | 保留已完成任务；问题和关联修改任务清晰可见                |
| 发布开关开启                   | 全部适用流程生成本次新证据，不能直接沿用历史绿灯          |
| 发布画面疑似异常               | 项目标红；用户确认对应新证据正确后转绿并保留确认记录      |
| 没有基准或采集失败             | 首次完整证据可人工认可；空白/不完整证据不能直接放行       |
| AI 自动判定通过                | 本次结果可为绿，用户认可基准保持原值                      |
| 发布开关关闭                   | 不因画面未运行或红色而阻塞；代码失败仍阻塞正式发布        |
| 诊断后代码/资源变化            | 旧结果只属于旧候选；发布新内容必须建立并检查新候选        |
| API/MCP 直接请求正式导出       | 与 UI 使用同一后端规则，不绕过检查                        |
| 当前 Beaver 开发及内部验证     | 本设计的全绿新限制不阻碍当前开发；失败记录保持真实        |
| 运行取消或 Beaver 重启         | 保留部分证据、可重跑，且不影响无关引擎/应用进程           |

后续原生应用验收遵守现有[全新测试流程](FRESH-TEST-WORKFLOW.md)及 `AGENTS.md`：使用新空白 Godot 项目，经 Beaver API 发起开发与测试，不直接编写游戏内容帮助应用通过。单轮内可连续重播和修复，同一流程在不同轮次需要重新通过应用建立。

初始设计交付只做文档检查。实际开发已执行编译、回归测试及独立 Godot 适配器验证；后者使用专用 fixture，不属于经 Beaver API 进行的游戏创建验收，不能代替上述原生应用验证。
