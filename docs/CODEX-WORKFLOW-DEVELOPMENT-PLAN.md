## 1. 已确认的目标和职责

Beaver 调用并管理 Codex；Codex 通过 MCP 或任务工具调用 Beaver，查询状态、提出计划、提交事实和请求后续操作。Beaver 持久保存主任务、阶段、子任务、执行记录、产物和验收结果，并负责依赖调度、暂停、恢复及界面展示。

Codex 负责理解需求、智能补充、选择性追问、提出与调整子任务、选择 Skills 和工具、执行制作、判断效果及处理失败。任何需要推理的环节都允许 Codex 参与，不以减少 AI 调用次数为验收目标；执行仍遵守任务期限和停止条件。

- 制作大阶段采用线性顺序：当前阶段通过约定验收后，后续阶段才能执行。阶段内允许局部迭代和动态拆分。
- Codex 提出子任务，Beaver 登记并管理。具备独立目标、恢复价值或验收要求的工作成为持久子任务；细碎工具操作关联当前执行记录。
- Beaver 保存并核验的状态是调度和界面的共同依据。Codex 的完成声明、计划文本和工具退出成功均不能单独使阶段通过。
- 一般创作中的低成本、可撤销细节可以自动补充；重要歧义根据现有自动强度与提问策略交给用户。本轮可选的 `deliveryPlan` 明确采用每阶段 owner 审批，适用于要求逐步查看交付的任务；自动验收策略留待后续实现。
- MCP、HTTP、桌面和动态工具入口复用同一套业务规则与状态，不各自保存进度或启动独立调度器。
- 一个资产场景保持单一写入者。阶段切换不强制新建 Codex 进程或 Blender 会话；会话可以复用，输入版本仍须明确。
- 用户修改上游要求时，保留旧结果与历史，暂停受影响的后续执行，重新确认受影响产物及验收。
- 运行中允许使用 Godot、Codex 和 Blender 插件；优先选择适合目标且能实际调用的插件来减少操作。记录发现、安装、启用、实际调用、版本及必要的重载状态，不能把已安装等同于可用。
- 制作小步骤按已有调研及最新可靠网络资料比较工具调用链，保留选择依据、候选产物、检查结果和问题。开发交付的批准与创作运行时每个动作的审批分别处理。

## 3. 工作流和调用约定

### 3.1 状态归属与粒度

逻辑层次为主任务、制作阶段、持久子任务、执行尝试、工具操作。实现应复用现有 task 身份和资产状态，明确关联关系；阶段状态由业务层维护，现有资产进度展示读取同一状态或其投影。

阶段不强制对应一个独立子任务或一个工作副本。多个子任务可服务于同一阶段，但不得同时写同一个 Blender 场景。现有 `beaver_submit_plan` 会结束规划会话并创建子任务，不能未经适配直接承担执行中追加局部计划的职责。

需要区分的生命周期含义：等待前置条件、可执行、执行中、待验收、已通过、失败、暂停、等待用户和结果待重新确认。具体枚举与存储形式在实施步骤 D1 确定；现有 `completed`、人工接受及新阶段验收的映射必须写清。

阶段进入已通过状态前，所需子任务和反馈必须按规则解决，产物与验证必须匹配当前输入。`autoAccept` 或人工接受不能绕过必需技术检查。任务结束、阶段通过与最终交付分别记录。

### 3.2 双向调用

```text
用户 / 观察界面 -> Beaver 业务层 -> 调度当前阶段 -> Codex
                                                   |
                     查询、计划、检查点、结果、问题 |
                                                   v
桌面 / HTTP / MCP / 动态工具 -> 同一 Beaver 业务层 -> 状态和证据
                                                   |
                                验收、恢复、后续调度 |
                                                   v
                                           界面及 Codex

Codex -> Blender / 插件 -> 场景、文件和执行结果 -> 关联当前执行记录
```

Beaver 派发时提供当前目标、已确认需求、有效输入、当前阶段允许的工作、可用能力及验收要求。Codex 回调的操作语义包括查询状态、提出或调整子任务、登记执行、保存检查点、提交结果、请求验收、报告阻塞和提出澄清问题；最终工具名在接口设计时确定。

变更调用按实际层级关联已有的主任务、阶段、子任务及执行尝试，并携带预期 revision 和请求标识；创建操作所需的新 ID 由 Beaver 分配。实际身份由 Beaver 绑定并校验，模型填写的 ID 不能自行授予跨任务权限。回调入口只暴露当前任务所需操作；外部 owner API 与受管理 Codex 回调的使用范围须区分。

业务层返回真实状态、更新后的 revision、处理回执和可采取的后续动作。请求接收、开始执行、产物提交、通过验收分别表示不同事实。

重复请求须返回原处理结果；同一请求标识携带不同内容应报冲突。断线后先查询处理状态，再决定是否重试。对 Blender 相对修改，数据库去重之外还须核验场景是否已经应用，不能承诺外部工具具有恰好一次执行语义。

耗时验证返回可查询的 operation 标识；回调不能持有数据库锁等待 Codex，也不能递归启动并等待另一轮 Codex。业务层保存转换后，由调度器在允许的边界推进后续工作。取消、超时和宿主重启必须留下可恢复状态。

### 3.3 实际输入、输出与验收

每次执行至少保存以下信息，字段可与现有记录复用：

- 输入：需求和模板版本、上游产物 ID、源文件及依赖哈希、参考资料、必要参数。对大型文件保存引用和清单，不重复塞入会话日志。
- 执行：阶段与子任务 ID、attempt、Codex thread / turn、Blender session / generation、开始与结束状态；实际使用的 Skill、工具和插件版本或内容摘要。
- 输出：候选 `.blend`、外部贴图及依赖、导出文件、预览、检查报告、文件哈希和对应输入版本。区分候选结果与已接受结果。
- 验收：检查器及规则版本、实际覆盖的要求、通过或失败项、技术报告、视觉评价来源及未解决问题。历史回执保留；输入、输出或规则改变后旧回执不可直接复用。

“提供了某个 Skill”与“执行中观察到了对应工具操作”分别记录。记录实际可见的请求、结果和文件，不推测模型内部推理，也不把无法观测的操作宣称为完整可重播执行。

实时观察帧关联 session、scene / view revision 和执行身份；用于验收的预览另需绑定提交产物。未保存的实时画面不得充当已保存文件的证明。会修改模型的准备或修复步骤产生新候选版本，随后重新检查该版本。

## 4. 实施步骤与完成条件

以下 D1-D8 按依赖顺序实施。复选框表示本轮通用代码及相关功能验证的完成状态；真实第三方插件和新增面板的原生交互证明单独记录，不能用单元测试替代。历史完成条件中涉及真实建模/插件验收的部分按用户最新范围延后。

### D1. 统一任务、阶段和执行的数据约定

进展：回调协议版本 5 复用 task / thread / turn、请求 ID 和双 revision。候选绑定模板、上游、文件 SHA-256、attempt 和 owner 决定；work 保存串行子任务及显式输入快照。新增配置 revision、固定命令/资源摘要、持久 operation、检查回执、模型/owner 评价和真实工具轨迹。既有阶段保持唯一状态源；历史未采集输入与显式空清单分别展示，不补造证据。

- [x] 明确主任务、阶段、既有子任务、执行尝试和产物的关联，确定每类状态的唯一写入者及转换规则。
- [x] 定义模板版本、输入输出清单、验收回执、请求去重和恢复所需的最小字段。
- [x] 为旧任务定义读取与恢复行为；缺少新证据的历史完成阶段不自动获得新的已验收语义，不重置现有任务或删除检查点。新增字段的默认读取和未绑定 Blender 会话的中断恢复有定向测试。

完成条件：用已有资产任务、串行子任务和一个中断任务样本核对数据约定；新增字段和状态有明确用途，阶段展示与调度不存在两套独立状态。

### D2. 接入统一的任务回调能力

- [x] 在现有业务层实现任务范围内的查询和变更操作，接入动态工具、业务目录及 MCP / API；复用既有传输。当前操作为 `state`、`receipt`、`report`、`stages`、`deliveryPlan`、`work`、`submitDelivery`。
- [x] 给受管理 Codex 注入当前任务的能力和执行身份，处理 turn 切换、旧回调拒绝及宿主端口 / 凭据生命周期；不把全局 owner token 写进提示词或日志。
- [x] 实现持久请求标识、revision 冲突、明确的未知结果响应和耗时操作查询，避免回调递归启动工作。

完成条件：同一操作通过不同入口得到相同业务结果；重复调用只登记一次；跨任务、过期执行与冲突内容被拒绝；查询、取消不被耗时验证阻塞。

进展：宿主注册 beaver_task 与 beaver_workflow，绑定执行身份并在协议升级时迁移线程。task.framework 复用桌面 / HTTP / MCP 核心业务。耗时文件回调及插件/检查/导出/扫描返回 operation，支持持久去重、查询、取消、状态 CAS 和启动中断恢复；callback 已提交而外层回执未提交的间隙可恢复。保留原同步回调入口。实际外部副作用不承诺恰好执行一次。

### D3. 接入线性阶段和资产子任务调度

进展：`deliveryPlan` 创建不可替换的 2-20 阶段模板；只有当前阶段可更新或提交。提交暂停旧 turn，owner 决定后排队恢复；返工失效下游批准且保留历史。`work` 支持当前阶段内按登记顺序执行子任务，同一资产工作副本最多一个 running attempt。`work.reopen` 可在无执行且无待审批时重开已完成步骤，失效该步骤及同阶段后续未取消步骤，解决完成后、提交前的依赖变化。资产步骤保存在主任务内，共用场景、输入及反馈，不创建独立调度任务和工作副本；普通代码规划任务沿用原机制。

- [x] 加载有版本的阶段模板，限制大阶段顺序；支持 Codex 在当前阶段提出或调整子任务，通过持久回执和 attempt 定义快照保留变更历史。
- [x] 资产子任务采用同主任务、同工作副本的串行记录，沿用主任务的资产能力、反馈、自动强度与场景归属，begin 绑定有效上游候选。该范围无需跨工作副本场景交接；不复用会创建独立工作副本的代码子任务展开逻辑。
- [x] 以验收结果解锁后续阶段；上游返工时阻止受影响任务继续使用旧输入；执行和恢复均保持单一场景写入者。

完成条件：两个最小阶段能够串行推进；只报告完成不能解锁后续阶段；执行中调整局部计划不丢失现有子任务，也不错误结束整个主任务。

### D4. 保存和关联实际制作证据

进展：冻结候选及输入复用内容寻址 blob 库，attempt 保存定义、身份、检查点与模型报告。实际 Codex 工具事件另存持久轨迹，started 绑定当时 attempt，迟到 completed 不归入新尝试；缺失事件保留证据缺口。inputExport 导出独立历史字节；检查器收到各 attempt 独立目录。通用 Blender 扫描器读取已保存文件引用并列出 unresolved，调用者仍须显式声明输入。最终依赖核验允许后续批准候选明确覆盖旧版本，拒绝未经批准的漂移。

- [x] 将可观察工具操作、检查点、场景身份、输入清单和输出清单关联到同一个 attempt；无法归属时明确记录缺口。
- [x] 提交时验证已声明模型及外部依赖存在且可读取，固定用于验证的候选版本；输出变化后失效对应回执。
- [x] 复用工作流哈希和日志能力，保存可查阅的产物及报告；为无法追踪的操作保留明确的证据缺口。

完成条件：能够从一个阶段追溯输入、实际执行、提交文件及检查结果；旧版本、缺文件和仅有聊天声明的结果不能作为有效交付。

### D5. 实现阶段验收与推进

进展：固定版本检查器对冻结候选执行规则，核验规则 ID/版本、候选和配置摘要，进程成功不替代规则 pass。owner 视觉判断绑定可解码的冻结 PNG，模型意见单独保留且不能满足 owner 门槛。配置或候选变更使旧回执失效；取消重检也不能复用先前通过结果。审批与最终合入共享技术/视觉门槛。规则覆盖和审美标准由后续适配器及制作步骤定义，本轮不承诺自动评价人物质量。

- [x] 执行已配置的技术检查，并核验检查定义、候选版本及报告归属；检查器运行成功不等于所有要求通过。
- [x] 保存视觉评价及其来源，区分程序检查、Codex 判断和用户决定；不承诺仅靠规则自动判断全部审美质量。
- [x] 保留逐规则报告/故障供 Codex 修复；修复生成新执行记录。沿用现有截止时间、停止条件和提问机制，不自动无限重试。

完成条件：通过、缺证据、检查失败、视觉待确认和旧回执分别有可验证的处理路径；阶段通过及后续解锁保持一致，人工接受不会掩盖技术失败。

### D6. 连接观察、反馈和恢复
