## 1. 讨论背景与已确认想法

现有创作关系继续保持：Beaver 管理任务并驱动 Codex，Codex 根据目标和上下文驱动 Blender 建模。用户希望在资产制作过程中看到实际变化，并能及时指导 AI 调整。

最初的想法是在 Blender 中固定一个观察摄像头，把画面同步到 Beaver，同时允许用户调整观察角度。讨论后将其定义为一个独立的资产制作任务窗口：左侧观察模型，右侧查看制作阶段并对话介入。这里的“固定”指稳定、独立的观察入口；观察方向允许旋转、缩放和平移。

已确认的产品要求如下：

1. 优先及时更新和视角操作流畅，接受近似预览效果；重操作期间明确显示忙碌和画面更新时间。
2. 使用独立窗口，可与 Beaver 其他页面并排查看；窗口服务于一个具体资产制作任务。
3. 同时支持文字描述、画面框选与标注、直接点选三维对象或部位。这三种方式均为刚需，首个完整版本必须具备。
4. 右侧展示 AI 当前制作流程，允许通过对话提交修改，并看到修改处理状态。
5. 同时保留“现在调整”和“完成后处理”两条途径。
6. AI 根据修改内容判断影响范围。局部修改可以插入当前流程，完成后继续原工作；影响已完成步骤时需要调整计划，并在有实质取舍时形成选项。
7. 是否将选项交给用户，服从 Beaver 现有“自动判断”策略。影响分析始终执行，自动判断决定由谁选择。

讨论中的两个典型例子必须保留为验收场景：

- 正在调整头发，用户说“鼻子小一点”。若确认影响局部，在安全切换点调整鼻子，检查结果，再继续头发。
- 用户说“腿长一点，胸大一点”。先判断对身体比例、已有服装及其他依赖步骤的影响；有必要时提供“重新实现服装流程”“无需重新实现服装流程”等选择，并说明各自约束。

“无需重新实现服装流程”仍可能需要局部适配或限制身体调整幅度。若两个要求无法同时满足，AI 必须说明取舍，不能宣称保留服装且任意修改身体都必然可行。

本任务聚焦观察、定位、反馈、排程与状态展示。最终高质量渲染、通用手工建模工具、多人协同编辑、完整操作录像暂不纳入本次设计；人物建模策略继续由对应 skill 负责。

## 2. 窗口与用户操作

建议在真实资产任务详情中提供“打开制作窗口”入口。窗口标题显示项目、资产和任务名称；有父任务时提供返回关联任务的入口。一个任务默认复用一个制作窗口，再次打开时聚焦已有窗口，不创建另一套任务执行状态。

窗口布局建议：

- 顶部：任务名称、连接状态、当前执行状态、最近画面更新时间。
- 主区域：实时模型预览；提供观察、框选标注、三维点选模式，以及旋转、缩放、平移和恢复默认视角。
- 右侧上部：制作阶段列表，突出当前阶段、被挂起阶段、需要重做或复核的阶段。
- 右侧下部：任务对话、当前选择的部位或标注附件、修改输入框及处理时机选择。
- 反馈记录：显示待处理要求、处理进展和相关决策，避免用户重复发送同一要求。

用户可以组合三种定位方式，例如先点选身体上的局部位置，再框选预览区域，最后输入“这里收窄一些”。提交前显示本条要求携带的截图和定位信息。

关闭制作窗口只解除观察订阅，任务继续执行。重新打开时从任务后端恢复阶段、反馈和最新画面。中止任务、关闭 Beaver 与关闭制作窗口具有不同的生命周期，界面不得混用。

窗口跟随具体资产执行任务。父任务存在多个子任务时，明确显示当前绑定的子任务；不得把反馈广播给所有子任务。后续任务产生新的任务 ID 时，显式更新窗口关联并保留来源链接。

## 3. 实时预览与三种定位方式

### 3.1 观察视图

观察视图读取 Blender 当前场景，包括尚未保存或导出的变化。视角操作由 Beaver 与 Blender 的直接通道处理，每次鼠标移动都不需要调用 AI。

建议维护独立的观察视图状态，与 AI 工作视角、当前选择、编辑模式和最终输出相机分离。优先验证独立视口或离屏视口采集；若实现需要观察相机对象，应明确标记并从正式导出和生产相机选择中排除。

拖动时允许降低预览分辨率或简化着色，停止操作后补发清晰画面。预览只保留最新待显示帧，视角命令可合并，避免网络或渲染变慢后继续播放过时的旋转操作。

Blender 的长时间 Python 调用、修改器计算或渲染可能占用主线程，造成画面和视角响应暂停。独立传输线程无法消除这一限制：

- 已知重操作正在执行时，显示具体操作及忙碌状态，保留最后一帧。
- 同时显示“最后更新于多久前”；只有连接存活而没有新画面时，不能显示为正常实时更新。
- 无法确认原因时显示“画面暂未更新”，不把所有延迟都解释成某个建模阶段。
- 主线程恢复后处理最新视角并更新画面；旧帧和旧视角响应不得覆盖新状态。

首版不预先承诺固定帧率。实施时记录实际设备、场景规模、分辨率、空闲与建模期间的更新间隔、交互到新画面的延迟，再确定可复现的性能验收目标。

### 3.2 文字描述

文字修改默认附带提交时的画面、实际渲染视角和场景版本。用户不需要为了表达“鼻子小一点”预先选择对象。

AI 应结合文字、画面和已有部位信息定位目标。目标不明确时再澄清，不能仅凭对象名称猜测成功。截图必须经受支持的图像输入或可读取的任务附件交给 Codex，并验证它确实被读取；只拼接一个图片路径不能作为视觉接入完成的证据。

### 3.3 画面框选与标注

框选、箭头或画笔等标注基于一张固定参考帧，记录图像尺寸和归一化坐标。建议在独立的定格标注画布中编辑，实时观察画面继续更新。用户始终能区分参考截图与当前模型。

窗口缩放、显示缩放比例和画面留白都必须纳入坐标换算。标注表示用户指出的画面区域，不自动等同于一个已确认的三维对象。

### 3.4 三维对象或部位点选

点击预览画面时，依据该帧对应的相机、投影和场景版本进行拾取。返回对象身份以及对象局部命中位置；必要时附实例身份、世界坐标、表面法线和当前几何信息。用高亮或标记让用户确认实际选中的位置。

鼻子、脸颊和身体可能属于同一个网格，仅返回对象名称不足以表达部位。语义部位标签可由人物 skill 提供，也可由 AI 结合局部命中和截图判断；不能把几何拾取成功直接宣称为语义部位识别成功。

建议为可观察对象维护稳定身份，处理重命名、复制和实例的区分。面索引、顶点索引和旧局部坐标只能作为当前版本的线索，重拓扑或对象替换后不得直接复用。

最小可靠策略是校验拾取所依据的场景版本：当前场景已改变且无法可靠重建旧帧对应关系时，返回“参考画面已过期”，刷新后重选。不得拿旧画面的屏幕坐标直接射向新几何并当作原目标。

## 4. 阶段列表与修改排程

### 4.1 阶段含义

制作阶段由 AI 根据资产生成，不固定为所有任务通用的“身体、服装、头发”流水线。建议阶段记录包含稳定 ID、名称、状态、依赖阶段、相关对象或部位、结果依据及所属制作轮次。

阶段可显示：待开始、进行中、已完成、暂挂、等待决策、需调整、需复核、失败。修改可以插入新阶段，也可以使已完成阶段重新进入调整或复核。没有可靠耗时依据时展示阶段状态和完成数量，不伪造百分比。

示例：头发进行中 → 头发暂挂 → 鼻子调整 → 局部检查 → 头发继续。身体比例变化后，原来已完成的服装可变为“需适配”或“需复核”。

资产内部阶段与 Beaver 的父子任务计划分别建模。一次头发调整通常不需要创建新的子任务；右侧同时提供阶段归属的任务信息，防止把整个项目计划当成当前资产的细分步骤。

### 4.2 “现在调整”

建议采用以下处理顺序：

1. Beaver 先持久化反馈及其参考信息，生成反馈 ID，显示“已接收”。
2. 将反馈提交给当前任务执行上下文；若 Blender 正在进行不可安全切换的操作，显示“等待当前操作完成”。
3. AI 核对目标、当前场景、原设计和已完成成果，明确确认理解的要求。
4. 分析对当前阶段、后续阶段和已完成依赖的影响，确定可直接调整、需要连带修改或存在实质取舍。
5. 存在取舍时生成有效选项、推荐、理由与重要性，交由现有自动判断策略处理。
6. 到达安全切换点后保存恢复依据，暂挂相关工作，串行执行修改并检查结果。
7. 更新受影响阶段及本条反馈状态，继续原工作；失败时说明结果和可恢复位置。

“现在调整”表达优先插入的意图，执行点取决于当前 Blender 操作是否可安全结束。不得并发运行两个场景写入者，或为了抢占而在未知状态强杀 Blender。

每条反馈至少区分：已接收、等待切换、AI 已确认、等待决策、执行中、检查中、已完成、失败或取消。底层 `turn/steer` 返回成功只证明消息已送达；AI 确认与实际修改完成都需要单独的证据。

### 4.3 影响判断与自动判断

AI 应说明预期影响的阶段、对象和结果，并区分局部适配、重新执行已有步骤、改变原设计三种后果。影响判断不能仅由“鼻子”“腿”等关键词或一个固定规则表决定。

身体调整影响服装时，选项可表述为：

- “重新实现服装流程”：允许按新比例重新适配或重做服装，说明可能变化的风格与工作量。
- “无需重新实现服装流程”：优先保留现有服装，说明局部适配范围及对身体修改的限制。

无法形成可行的保留方案时，不能提供虚假的可选项；应提出实际可行的替代方案。采用推荐后，记录选择来源、理由和受影响阶段，并按选择执行。

复用现有 `askRatio` 语义：0 对有效推荐自动选择；100 将实际产生的问题交给用户；10、30、70 按重要性阈值决定。它们不代表每若干次对话必须询问一次，也不要求每条局部修改都生成问题。

任务可覆盖或继承全局档位。已经等待用户回答的问题不能因档位变化而自动提交；保留现有填写推荐答案与显式提交的交互。该策略仅处理创作决策，不改变工具权限。

### 4.4 “完成后处理”

提交后立即保存为待处理要求，在当前制作轮次完成前不将其作为立即执行指令交给 AI。执行时重新检查届时的模型和依赖关系，延期不会消除修改的影响。

建议将“当前流程”定义为当前资产的一轮制作阶段，而非单次 Codex turn 或整个游戏项目。当前轮次完成并完成该轮检查后，再开启调整轮次。新修改所需的适配、检查和最终导出仍需完成。

为避免后续任务消费尚未处理修改的资产，待处理队列应在任务最终交付、变更合入和依赖子任务放行之前检查。队列检查与结束决定需要在同一个任务串行处理边界内完成；不能先宣布任务完成，再静默继续修改同一交付结果。

若用户提交时原任务已经交付，沿用 `task.followup` 创建后续任务，保留独立回退边界，并将新任务关联到原资产。接收反馈与结束任务同时发生时，必须明确返回反馈归入哪一轮或哪个后续任务。

### 4.5 队列与恢复

反馈由后端持久化，窗口的本地状态只作为显示缓存。建议提供未开始反馈的编辑、撤回；已经执行的修改通过已有后续修改或回退流程处理。

同一资产的修改串行执行。多条要求有顺序和独立 ID；可以分析重复与冲突，但不能未经说明丢弃早先要求。“现在调整”与“完成后处理”的优先级不同，后提交的要求不会自动取消前一条。

任务处于 `awaitingInput` 时仍可观察和保存新反馈；问题答案继续通过 `task.answer` 提交，新要求进入队列。不能将新要求伪装成选项答案或直接调用不适用于该状态的继续操作。

重试、断线和窗口重开不能重复提交同一修改。进程在实际修改后、完成回执前退出时，标记为待核验，恢复后检查场景与记录，避免再次执行“加长一点”等相对修改。Beaver 重启后不自动恢复模型消耗，仍遵守现有显式继续规则。

## 6. 建议技术方案

### 6.1 三条职责通道

建议采用 Blender 观察视图采集、原生后端转发、任务窗口显示的方案，不依赖频繁导出整个模型才能更新画面。

1. 观察通道：Blender 生成预览帧，原生后端将帧、视角和场景版本转给窗口；视角与拾取命令沿同一任务绑定关系返回。
2. 任务通道：Beaver 保存反馈和制作状态，利用现有任务执行上下文交给 Codex；Codex 驱动建模并报告处理结果。
3. 决策通道：Codex 报告影响与选项，复用 `beaver_ask_user`、自动判断及答案记录。

高频画面和鼠标事件不逐条写入任务数据库，也不逐条拼入 LLM 上下文。低频的用户要求、参考截图、决策、阶段变化和修改结果需要持久化。

### 6.2 预览桥与传输

拟采用独立的本机预览桥，承载二进制压缩帧和结构化控制消息，首选验证本机 WebSocket 方案。该选择尚未实测；第一阶段需同时核对现有 IPC 与二进制资源响应能否满足要求，优先复用能够达标的原生能力，避免增加不必要依赖。

Blender 网络线程只处理传输及有限队列。读取或修改 `bpy` 场景、视图和拾取信息应回到受控的 Blender 主线程执行；不要在后台线程直接调用场景 API。

预览与建模工具可以使用不同传输连接，但场景仍由同一 Blender 实例和单一写入序列负责。预览桥不另行接管模型制作，不暴露任意 Python 执行接口。

通道绑定项目、任务与受管会话，使用会话级凭据或等效校验，限制在本机通信。新增窗口和连接需要精确补充 Tauri capability、CSP 与事件作用域，禁止用全开放配置代替接入设计。

没有订阅者时暂停或显著降低采集；网络、解码、帧队列和参考截图保留量均设上限。窗口断开后释放订阅与显存资源，任务所需 Blender 会话的释放另行判断。

### 6.3 最小数据契约

以下为拟定的协议字段职责，名称可在实施时对齐现有类型。版本号、身份与状态校验必须保留，不能仅靠时间戳或对象名称关联。

| 记录       | 需要表达的信息                                                               | 主要约束                                                   |
| ---------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 会话       | 协议版本、projectId、taskId、执行轮次、blenderSessionId、能力与连接状态      | Blender 重启生成新会话身份；历史消息不能控制新会话。       |
| 画面       | frameId、sceneRevision、viewRevision、采集时间、尺寸、格式、实际视图及投影   | 元数据对应真实采集状态；场景重载必须使旧版本失效。         |
| 视角命令   | 任务与会话身份、序号、目标视角或规范化操作                                   | 合并高频操作，仅按当前序列应用；视角变化不冒充模型修改。   |
| 拾取结果   | 参考帧、对象与实例身份、局部命中、可选语义标签、有效性                       | 版本过期必须拒绝或重新确认；拓扑索引不保证跨版本稳定。     |
| 反馈       | feedbackId、处理时机、文本、截图引用、标注与拾取引用、提交时间、所属制作轮次 | 接收先落盘，重复 ID 不生成第二次修改；图像和附件必须可读。 |
| 影响与决策 | 受影响阶段、原因、可行方案、推荐、重要性、选择与来源                         | 推荐元数据服从现有校验；保留采用时的策略与选择依据。       |
| 阶段与回执 | 稳定阶段 ID、状态、依赖、计划版本、关联反馈、结果依据                        | 后端检查任务和版本；消息送达、AI 确认、修改完成分别记录。  |

连续视频帧只做有界缓存，用户提交反馈所引用的画面作为任务附件保留。附件应由 Beaver 通过受控路径交付给任务工作区；内容大小与路径访问遵循现有资源边界。

优先复用 `turn/plan/updated` 展示基础计划，再增加最小结构化上报入口表达阶段依赖、影响与反馈回执。自然语言日志可以补充说明，不作为确定“已完成”或“可以重做服装”的唯一机器依据。

### 6.4 任务与会话生命周期

当前受管 Blender 会随执行调用结束而关闭。为支持边观察边回答问题，建议把会话所有权提升到资产任务运行时：运行中和等待用户决策时保留同一场景，短暂的 Codex 会话切换不自动丢弃模型现场。

至少在阶段边界、重大修改前和最终交付前建立可恢复依据，通常包含已保存场景、阶段记录和反馈 ID。停止操作无法及时完成保存时，明确说明可能未保存的变化；不能把最后一张截图当成可恢复的模型。

任务完成后停止实时流，显示最后画面及已保存资源的预览入口；不得把成品文件预览标成仍与 Blender 实时同步。再次修改沿用后续任务边界。

中止、失败、应用退出、场景重载和进程崩溃都需明确释放或恢复策略。普通视窗关闭只退订；任务结束和应用退出清理本任务拥有的进程；崩溃后失效旧拾取并从有效保存点恢复。原生应用重启保持等待显式继续，不自动启动付费执行。

### 6.5 拟定代码职责

后续实施按责任拆分，以下为模块建议，不是本次创建的源文件清单：

- 原生任务核心：反馈存储与队列、制作阶段投影、最终交付前的待处理检查；复用现有执行与自动判断逻辑。
- 原生桌面：任务窗口管理、预览会话和传输、面向 UI/API 的业务路由；高频预览不长时间占用全局 store 锁。
- Blender 桥：连接与主线程调度、观察视图采集、拾取，各自管理明确的资源生命周期。
- 前端：任务窗口容器、预览交互、标注与反馈输入、阶段列表；抽取可复用的真实对话能力，避免复制大组件。
- 共享协议：任务身份、预览状态、反馈和阶段的类型与校验。

修改 `codex_home.rs`、`scheduler.rs`、任务结束逻辑、`shell.rs` 和公共类型等接入文件时，由一名集成负责人统一处理。遵守现有有效代码行数规则，不借此增加历史超大文件基线。

## 9. 验收标准

以下为真实集成验收要求，目前尚未取得本分支原生验收通过记录；已完成的工程检查见第 11 节。

1. AI 在 Blender 中修改模型但尚未导出时，制作窗口能看到变化；画面与指定任务、场景一致。
2. 旋转、缩放、平移和恢复视角可以直接操作；不增加对应鼠标事件的 LLM 请求，不改变 AI 工作视角或正式输出相机。
3. 重操作期间显示忙碌或准确的未更新状态；最后画面时间可见，恢复后没有积压旧视角连续回放。
4. 文字反馈携带正确参考画面并被 Codex 实际读取；框选、标注在窗口缩放、留白和高 DPI 下仍对应同一区域。
5. 点选一个网格上的鼻子与脸颊能表达不同局部位置；对象改名、实例、修改器及拓扑变化有明确校验，过期选择不会悄悄改到其他位置。
6. 调整头发期间提交“鼻子小一点”，能看到接收、等待、执行和检查状态；完成鼻子调整后继续头发，阶段记录真实。
7. 提交“腿长一点，胸大一点”，能够根据实际服装依赖提出可行取舍，执行选择并复核受影响成果。分别覆盖手动询问、自动推荐及中间阈值。
8. “完成后处理”在当前制作轮次结束前不提前修改；跨 Codex turn 不丢失。阶段完成与反馈接收同时发生时不丢单、不重复、不过早交付。
9. 同一反馈重试不会重复修改；修改后尚未收到完成回执就断线时，恢复先核验。后续任务保留独立的交付与回退边界。
10. 等待用户回答时模型现场可继续观察；关闭和重开任务窗口不停止任务。两个资产任务的画面、选择、反馈和相机状态互不串线。
11. Blender 重载、退出或崩溃后显示真实状态并失效旧选择；恢复来源明确，不声称恢复了没有保存的场景变化。清理仅针对任务拥有的进程。
12. 制作阶段能插入、暂挂、恢复和重新复核；原有任务对话、自动判断、父子任务推进及成品预览没有回归。

工程验证应匹配实际改动：前端类型与相关交互测试、原生相关单元与契约测试、Blender 桥的边界测试、官方格式检查和 `npm run check:effective-lines`。重点覆盖版本错配、队列竞争、相对修改重放、自动判断阈值和会话释放；避免只复述实现逻辑的测试。

真实原生验收遵守项目现有规则：使用 `scripts/start-fresh-native-test.ps1`，构建新测试程序时传 `-Build`；每次重大验收从新的空白 Godot 项目开始，只通过 Beaver API 完成游戏创作流程，不直接编写测试游戏资产或绕过 Beaver 驱动 Codex、Godot、Blender 来补齐结果。通过 API 提交用户指令，再观察真实窗口和应用状态。

启动验收实例前通过现有机制处理旧 Beaver 实例；不要按进程名终止 Blender、Godot 或无关程序。Windows 原生构建与测试保持同一 PowerShell 工具链环境和现有 MSVC `LIB`，保留独立验收目录与证据。
