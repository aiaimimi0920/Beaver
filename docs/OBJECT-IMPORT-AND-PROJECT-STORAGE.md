# 对象导入与项目 .beaver 存储规范

日期：2026-09-15。设计版本：v0.1。状态：后续实现规范，尚未开发；本次不修改程序或现有项目，不更新 UI、不编译 exe。

本文补充 [对象创作框架开发设计](OBJECT-CREATION-FRAMEWORK-DESIGN.md)。第 1 节为用户确认的要求，其余为据此制定的实现约束和建议目录；具体文件名、schema 和接口可以在实施前调整。现有 [UI mock](ui/OBJECT-UI-PREVIEW.md) 仅演示文件选择与表单，不代表三种导入方式已经实现。

## 1. 已确认的要求

对象导入统一从目标项目的“导入对象”入口开始，支持以下三种来源：

| 方式              | 来源选择                                                  | 后续选择                                       |
| ----------------- | --------------------------------------------------------- | ---------------------------------------------- |
| 文件 / 文件夹导入 | 选择一个或多个外部文件、一个或多个文件夹                  | 查看待导入内容、确认对象归组，填写额外信息     |
| 项目导入          | 从已经添加到 Beaver 的项目中选择来源项目                  | 读取该项目对象列表，再选择一个或多个对象       |
| 第三方项目导入    | 选择尚未添加到 Beaver、但具有 Beaver 项目结构的项目文件夹 | 自动读取项目中的对象信息，再选择一个或多个对象 |

“已添加项目”包括当前打开的多个项目及已登记但暂未打开的项目。后两种方式使用相同的对象读取、选择和导入规则，区别仅在来源项目的定位方式；第三方项目无需先加入 Beaver 的项目列表。

以后通过 Beaver 新建项目时，必须在项目根目录创建 `.beaver/`。Beaver 保存的该项目信息统一存储于此，随项目目录一起携带；对象浏览和导入不能依赖源机器的应用全局数据库才能识别项目内容。

本次只确定规范。具体导入逻辑、项目存储改造和旧数据迁移均留待后续实施。

## 2. 导入界面与操作流程

导入弹窗提供“文件 / 文件夹”“项目”“第三方项目”三个来源入口。始终显示目标项目，用户在弹窗中切换来源不会改变目标；多项目同时打开时，以发起导入时的目标项目身份绑定本次操作，提交前再次核对，避免写入后来切换到的页面项目。

文件 / 文件夹方式提供多文件选择及文件夹选择，可以多次添加文件夹并累积到选择清单，支持移除和去重。展示具体文件及归组结果，不以同目录、相同扩展名或名称相近直接判定对象归属；用户可以将内容组合为一个对象，或拆成多个独立对象。例如人物模型与其贴图可以组成一个人物对象。

项目方式先显示 Beaver 已登记的项目，再显示选中项目的对象。第三方项目方式先选择项目根目录，检查 `.beaver` 结构、格式版本及对象清单，随后进入相同的对象选择视图。浏览第三方项目不自动登记、升级或修改源项目；若所选目录实际已登记，复用已登记身份和读取路径。

对象选择视图展示对象名称、类型、实际缩略图或明确占位、标签、可导入版本和依赖，支持搜索、筛选与多选。文件方式进入归组后的对象确认视图；项目方式沿用已有对象结构，不重新根据文件格式猜测对象。

确认视图允许调整目标对象的名称、类型、标签、说明等附加信息，展示将导入的对象、组件、依赖与目标路径。对来源信息的展示和编辑分开，用户修改目标名称或标签不改变源记录。最终确认时才启动导入，完成后可定位到新对象；取消预览不生成对象。

选择了普通资源目录但没有有效 `.beaver` 结构时，第三方项目入口给出原因并允许用户改用文件 / 文件夹方式，不伪造对象清单。缺少清单、格式损坏或版本不支持须有对应提示，不能显示成“项目没有对象”。

## 3. 对象复制、依赖与任务边界

三种方式最终进入同一对象导入服务。默认复制为目标项目内可独立修改的新对象，保留源文件；目标项目不持有对源项目对象的写入权，也不建立随源项目变化而自动更新的连接。源、目标对象继续分别遵守对象串行修改规则。

项目方式默认读取明确的已接受版本，在选择时固定版本身份、清单及内容哈希。源对象正在修改时仍读取其已接受版本；尚无可导入版本时显示原因，不将工作区中的半成品自动视为可用版本。未接受候选或完整创作历史的导入不在本轮默认契约中。

复制对象自有组件，并计算独立对象引用的依赖闭包，向用户展示自动加入的依赖。依赖对象在同一批次仅复制一次，共享引用仍指向同一个目标依赖对象；记录源项目、对象、版本到目标身份的映射并重写引用。只按名称或文件路径相似不能复用目标对象。缺失依赖需补齐或明确处理，否则受影响对象不能提交为完整导入结果。

目标对象、组件和版本使用新的本地身份；来源项目 ID、对象 ID、版本、导入时间、请求 ID 和内容摘要保存在来源记录中。已接受状态及源审批作为来源证据保留，目标初始状态标为“已导入、待验证”，完成目标所需检查和接受后才成为可供正式下游消费的版本。外部文件没有创作任务时，不补造历史任务或验收记录。

默认不复制来源项目的活动任务、排队项、写入锁、可执行会话和运行进程。目标用户要求进一步调整时，再创建目标对象的中修及精修任务。导入的进度和错误属于持久导入操作；需要 AI 制作的动作再进入统一任务链，避免导入入口绕过对象写入队列。

同名对象和文件冲突在确认前展示，默认创建独立对象并分配不冲突的路径，不覆盖目标已有文件。更新现有对象属于后续独立的修改能力，必须进入该对象的串行队列。源目录与目标相同或同一项目的目录副本应明确提示，独立复制也使用新对象身份。

一次导入使用稳定请求 ID。同一请求的重试、重复点击和恢复复用原映射及回执；用户明确再次导入才产生新的独立副本。先准备内容和引用，核验后再提交对象登记；文件与数据库通过可恢复操作日志协调，失败或取消不得留下被误判为完整可用的半个对象。发布采用既有框架的项目物化协调规则。

## 4. 项目 .beaver 存储边界

`.beaver/` 是该项目 Beaver 管理信息的权威存储。包含项目身份、设计与蓝图、对象登记和组成、版本及固定引用、任务与父子关系、队列和创作轮次、阶段与验收规格、输入输出清单、备份和恢复证据、预览与反馈、导入来源与操作回执，以及项目级配置。恢复这些记录所必需的内容、日志和工作区也归属该目录，不能只保存指向原机器应用数据目录的路径。

游戏资源与代码仍位于引擎可正常使用的项目目录，例如 `project.godot`、场景、模型和贴图；`.beaver` 记录其所有权、版本和相对路径，并保存恢复需要的冻结内容。引擎自己的缓存保持引擎约定。普通对象列表、素材枚举、游戏构建和交付内容不把 `.beaver` 的数据库、工作区或证据当作游戏素材递归导入；完整项目备份则必须包含 `.beaver`。

应用全局数据只保存宿主级信息，例如已登记项目路径、最近打开记录、全局偏好、账号凭据和机器工具安装位置。项目列表及跨项目任务查询可以使用可重建索引，但项目内容和状态的权威记录必须在各自 `.beaver` 中，不允许全局数据库与项目目录各维护一份可独立修改的项目状态。模型凭据和机器授权不随项目复制。

建议的职责布局如下，文件名与格式须在实现时定稿，当前不会创建这些目录：

```text
<项目根>/
  project.godot
  <游戏资源与代码>/
  .beaver/
    project.json          # 稳定项目 ID、存储格式版本、名称和创建信息
    project.sqlite        # 项目配置、对象、任务、轮次、队列、验收和事件
    content/              # 清单引用的冻结内容、版本与检查点
    workspaces/           # 活动任务或创作轮次的隔离工作区
    previews/             # 版本预览及反馈实际使用的冻结画面
    evidence/             # 检查报告、执行记录及恢复所需项目证据
    operations/           # 导入、物化和迁移的文件操作日志及回执
    cache/                # 可重建缓存，与不可丢失内容明确区分
```

`project.json` 仅保存项目识别所需的最小信息，不重复存储可变对象清单。对象列表从版本化的项目存储读取，目录中不能再出现第二份未约定同步规则的对象真相。临时文件和锁也放在 `.beaver` 内；锁的存在与否不能单独证明制作任务已结束或可自动恢复。

项目内文件引用尽量使用相对根目录的路径和稳定身份，目录移动不改变项目 ID；应用登记路径属于本机定位信息。完整复制项目造成相同 ID 出现在不同目录时，检测并提示是迁移位置还是创建独立副本，不合并两处任务状态；独立副本显式生成新项目身份并保留来源。仅浏览第三方项目不能修改其身份。

多个项目可同时打开，各自保存独立记录与修改队列；同一项目的多个窗口共用受管核心，外部第二个宿主不能各自启动同一轮任务。存储离线或不可写时展示状态，禁止退回全局库继续写另一份项目数据。

新建项目只有在引擎项目文件、`.beaver` 最小清单及存储初始化成功后，才报告创建成功并登记到项目列表。失败保留可诊断状态，不把半初始化目录列为可正常使用的 Beaver 项目。

## 5. 两种项目来源共用的读取规则

项目读取器以项目根目录解析 `.beaver`，返回项目身份、格式版本、对象摘要、可导入的版本和内容读取能力。已登记方式先由应用登记表获得路径；第三方方式由用户选择路径。之后的对象发现、校验、依赖计算与复制完全共用，UI 只负责选择和展示。

已打开源项目通过受管服务取得一致的已提交快照，不直接复制正在变化的工作区。外部项目采用不会修改源库、触发迁移或自动续跑任务的读取方式；使用 SQLite 时必须处理 WAL 的一致性，不能只复制主库，也不能用普通可写 Store 打开源目录。无法获得一致快照时明确要求重试或停止源写入，不能拿不完整状态继续。

读取时核对格式版本、身份、清单及文件存在性，复制时核对内容哈希，并在提交前确认仍是所选快照。源项目后续变化不替换本次已固定输入。目录外依赖、绝对路径和链接不得静默越出选择范围；需要用户补充的内容明确列出，不能遗漏后仍宣称对象完整。

浏览项目或导入资源不自动运行其中的脚本、插件安装或制作任务。后续使用对象时再按创作框架声明并准备所需能力，保留源工具与插件版本信息用于检查。

以下是 2026-09-15 的代码抽查，说明后续改造位置；不能据此声称已满足本规范：

- [`store.rs`](../native/core/src/store.rs) 第 19-39 行在应用数据根创建 `beaver.sqlite`，包含实体、任务事件和调用记录；当前项目相关数据仍使用该全局 Store。
- [`types.ts`](../src/shared/types.ts) 第 22-37 行的 `Project` 包含项目 ID、路径、design 和 blueprint；目前没有本文的新项目存储契约。
- [`files.rs`](../native/core/src/files.rs) 第 69-80 行已排除 `.beaver` 与 `.beaver-context`，但这只证明素材遍历有排除规则，不代表项目持久化已迁入 `.beaver`。
- 现有 TS 路径见 [`projects.ts`](../src/core/projects.ts) 和 [`store.ts`](../src/core/store.ts)。实施时核对仍需支持的入口，沿用共享核心，不为不同入口维护两套项目格式。

旧根目录 `beaver.project.json`、项目相关全局实体/任务/事件、应用数据下的工作区和引用内容，以及 `.beaver-context` 等项目专用信息，都需要在存储改造中列清迁移范围。`.beaver-code-structure.json` 等已有工具直接读取的根目录文件需要同步调整读取器和随程序分发的指令，不能只移动文件使旧规则失效。引擎要求的 `project.godot` 等继续保留在原约定位置。

迁移沿用 [完整备份与恢复契约](DATA-MIGRATION.md) 的保护原则：先备份并验证恢复所需内容，停止相关项目写入，再准备新的 `.beaver` 数据与 ID/路径映射，验证后切换权威存储，记录迁移版本和完成回执。失败保留原数据和诊断结果，不删除旧库、不提前宣称转换完成；成功后旧副本仅作受控备份，不继续双写。旧客户端遇到新结构不得通过旧写路径修改它。

未登记的历史目录如果只有 `beaver.project.json`，对象信息仍在另一台机器的全局库中，单凭该目录无法恢复对象列表。提示需要完整旧数据迁移或显式按文件导入，不根据文件猜测已丢失的对象身份。完整项目迁移和对象复制保留各自的回执及身份规则。

## 7. 实施顺序与定向验收

后续先建立项目本地存储、新建初始化及旧数据迁移，再完成对象契约和共用项目读取器；随后依次接入文件 / 文件夹来源、已登记项目来源和第三方项目来源，最后接入真实 UI。项目来源依赖同一读取器，不能两套解析分别迭代到不兼容。当前 UI 优化阶段继续保持 mock。

按各批实际改动验证下列行为，不要求每批运行全部场景或全流程测试：

1. 新建空项目即有有效 `.beaver`；初始化失败不报告成功，目录移动后仍能读取原项目身份与对象信息。
2. 在独立 Beaver 数据目录中读取完整项目副本，可以发现对象和版本，不依赖原宿主数据库或绝对路径。
3. 多文件、多文件夹累积选择、去重、归组和附加信息进入目标对象，取消后目标无新对象。
4. 已登记入口与第三方入口读取同一来源快照时得到相同对象和依赖；第三方浏览后源目录及本机项目登记表不被改写。
5. 多项目打开并切换页面后，导入仍写入明确确认的目标；源对象继续修改时不会改变已固定的导入输入。
6. 人物与贴图等自有组件完整复制；多个对象共享的独立依赖只复制一次；移除源项目后目标引用仍能解析。
7. 同名冲突不覆盖已有对象；重复提交不重复生成身份；取消或中断后的恢复不会暴露半导入对象或启动来源任务。
8. 缺少 `.beaver`、未知格式、依赖缺失、源目录不可读、数据损坏及不可取得一致快照均返回具体原因，不伪装成空对象列表或导入成功。
9. 小型旧项目样本迁移后，项目、任务、对象来源和相关文件可定位；中断与重试保持映射，原备份及恢复路径可用。

文档阶段只检查文档格式、链接与仓库规定的有效行检查，不递增应用版本、不运行功能测试或重新打包。本文全部实现项仍为待开发。
