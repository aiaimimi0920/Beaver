# Beaver 技术选型复盘

## 结论

是的，针对 Beaver 的产品定位和你明确提出的轻量发布要求，更换为 Tauri 2 + Rust、保留 React 界面，比继续使用 Electron 更合适。最初选型偏重快速实现，低估了分发体积与产品定位的重要性；这属于选型权衡不充分，而不是你的需求不合理。

## 为什么最初会选择 Electron

从现有实现能确认，项目采用 React / TypeScript，原启动入口是 Electron，主进程入口为 `dist/main.cjs`。这条路线的工程便利是：

1. 前期 HTML 交互原型容易延续到正式 React 界面，适合频繁调整布局。
2. 界面和后台可以共用 TypeScript 类型、校验和数据结构，减少初期跨语言成本。
3. Node 便于接入文件读写、进程控制、网络请求和命令行工具。
4. Electron 自带浏览器运行环境，减少不同系统 WebView 带来的界面差异。

这些可以解释这条技术路线为什么容易被采用，但不是必须使用 Electron 的理由，也不能当作当时已经做过完整选型对比的证据。没有充分依据声称当时已经验证过 Loom、Hook 和 Beaver 的同口径发布体积。

真正的问题是：我把开发端的便利放在了用户端的安装成本之前，没有及早建立发布体积预算并交付最小安装包验证。

## 为什么轻业务也会有大体积

Electron 将 Chromium 和 Node.js 嵌入应用；即使业务主要是任务编排，也需要承担这一运行时底座的分发成本。业务计算量小，并不意味着底层框架体积小。[Electron 官方介绍](https://www.electronjs.org/docs/latest/)

不过，不能只凭这一点断言某个 240 MB EXE 的每一部分都来自框架。单个 EXE、完整未压缩发布目录、压缩安装包和安装后的依赖占用是不同口径，必须分别测量。删除无用资源和调整打包可以消除浪费，但不能把 Electron 的运行时底座当成普通业务代码彻底裁掉。

## 更合适的分工

| 层级 | 选择 | 职责 |
| --- | --- | --- |
| 界面 | 保留 React / TypeScript | 创作看板、对话、资料编辑、素材浏览、设置 |
| 桌面宿主 | Tauri 2 | 窗口、托盘、系统集成、前后端通信 |
| 本地服务 | Rust | 任务生命周期、文件保护、数据库、回退、进程管理、凭据保护 |
| 外部创作工具 | 独立检测与安装 | Codex、Godot、Blender 及所需插件、MCP、skill |

Tauri 使用系统 WebView，能够继续采用 Web 前端，而不要求每个应用再随包携带完整浏览器。这里选择它是基于 Beaver 现有界面的复用价值与轻量部署目标，不是断言它对所有桌面应用都优于 Electron。[Tauri 官方介绍](https://v2.tauri.app/start/)

不建议为了缩小体积，连已经反复确认的界面都推倒重写；也不建议只更换窗口外壳，却在后台继续藏一套 Electron 或 Node 业务服务。

## 必须正视的代价

- Node 主进程业务需要迁移，不是换一个打包配置即可完成。
- 任务中止、恢复、并发文件冲突、退出时清理子进程、旧数据和密钥兼容都必须重新验证。
- 系统 WebView 存在平台差异，Windows、macOS、Linux 仍需各自进行实际测试。
- 零环境安装不等于零依赖。系统 WebView 和外部创作工具的下载及安装成本必须单独公开，不能用一个小 EXE 掩盖实际安装成本。
- 不能把功能不完整的原生预览程序体积，直接当作最终产品体积。

## 当前状态与验收

本次核对确认仓库已经存在 Tauri / Rust 迁移实现及原生构建入口，但默认 `start` 和 `package` 仍走 Electron。迁移文档也明确标注尚未完成。因此当前不能宣布已经彻底更换或完成交付。

验收应以功能完整、原有数据可迁移和回退、后台任务行为正确为前提，再验证完整未压缩 Beaver 发布载荷不超过 50,000,000 字节；外部工具与系统依赖另列清单。

简而言之：最初选择 Electron 是为了更快实现，但对于你的产品，轻量分发本应是先验约束。现在应修正这个权衡，而不是要求你接受两百多 MB 是理所当然。
