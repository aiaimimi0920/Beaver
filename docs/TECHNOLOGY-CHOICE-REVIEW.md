# Beaver 技术选型复盘

## 结论

是的，对 Beaver 这样的产品，改用 Tauri 2 + Rust、保留 React 界面，比继续采用 Electron 更符合你的要求。

最初选 Electron，实质上是优先考虑了开发便利和原型交付速度，没有充分把轻量发布、零环境上手，以及与 Loom / Hook 的技术一致性作为选型约束。这是选型权重的问题，不是你的需求导致应用必须有 200 多 MB。

这里需要说明：仓库可以证明使用了哪些技术，不能单凭当前代码证明最初每一个决策的心理过程。下面是依据现有实现做的工程复盘，而不是伪造一份当时已经做过的选型论证。

## 为什么 Electron 容易成为最初的选择

- 界面采用 React / TypeScript，桌面主进程也使用 TypeScript，可以快速贯通界面、文件操作、进程调用和消息通信。
- 任务编排需要启动外部程序、读取日志、操作文件与调用 API，Node 的现成接口便于快速实现。
- 内置浏览器运行时，可以减少不同操作系统 WebView 差异带来的界面适配工作。

这些理由可以解释它为什么适合快速原型，但不能证明它最适合 Beaver 的正式产品。尤其是“需要调用 Codex、Godot、Blender”并不等于“必须使用 Electron”。Rust 同样可以管理子进程、标准输入输出、文件、网络和后台任务。

## 为什么与你的产品目标不匹配

Electron 发布物携带 Chromium、Node 及配套运行时。即使业务只是编排，这些固定成本也不会随着业务变轻而消失。重处理多少与安装包大小并不是同一件事。

你希望 Beaver 是轻量的创作入口：负责界面、项目与素材归档、任务会话、环境准备，而把实际创作交给外部工具。为了这个入口额外携带一套完整浏览器运行时，不符合你明确提出的体积要求。

Loom / Hook 是应该优先检查的本地参照。不能先选方便开发的方案，再把明显超出预期的体积解释成不可避免。应该在原型阶段就构建发布物，把真实体积纳入选型验收。

## 更合适的分工

| 层级 | 技术与职责 |
| --- | --- |
| 界面 | 保留 React / TypeScript，避免为了换桌面宿主重写全部 UI |
| 桌面宿主 | Tauri 2，负责窗口、托盘与原生通信 |
| 本地核心 | Rust，负责持久化、文件保护、任务调度、进程生命周期和凭据处理 |
| 创作工具 | Codex、Godot、Blender 独立安装，由 Beaver 管理环境准备与调用入口 |
| 后续云执行 | 通过执行接口扩展，而不是把首版本机功能变成强制云依赖 |

这里更换的是桌面宿主和本地核心，并不是否定网页界面，也不是重新开发整个产品。

## 必须正视的代价

- Node 主进程业务不能仅换一个窗口壳就自动变成 Rust；任务恢复、并发冲突、回退、凭据及素材协议都需要逐项迁移验证。
- Windows 使用 WebView2。安装体验需要检测并补齐依赖；应用自身发布载荷与首次安装额外下载量必须分开披露，不能把外置运行时当作成本消失。
- 不应通过另藏 Node / Electron 后台来制造“EXE 很小”的假象，也不应只比较一个 EXE 而忽略整个目录。
- Tauri 不会自动保证任务稳定、内存更低或跨平台无差异；这些仍需要真实运行验收。

## 当前事实与验收口径

本次核对确认：仓库仍保留 Electron 44.2.0 依赖；同时已经存在 Tauri / Rust 迁移工作。`docs/NATIVE-MIGRATION.md` 明确记录迁移尚未完成，旧发布包仍是功能对照和回退入口。

现有较小的原生宿主样本只能说明体积方向可行，不能代替完整业务迁移后的发布验收。本次只复核选型，没有重新构建，也没有完成迁移。

最终应以完整未压缩 Beaver 发布载荷不超过 50,000,000 字节、没有隐藏 Electron / Node 运行后台，并且既有任务、数据、素材和导出能力得到验证作为验收条件。外部创作工具及系统运行时另外列出下载和磁盘成本。

简而言之：Electron 让最初的开发更快，但没有很好地服务你的产品约束；继续为其固定体积做压缩修补，不如保留 UI、迁移到 Tauri / Rust。最初应该更早进行这项判断。
